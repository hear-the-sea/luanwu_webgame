# 性能优化复核与下一步候选（2026-09-30）

复核发现一处 MySQL 排序规则兼容边界，已修正。疗伤和 WebSocket 未发现本轮引入的业务或鉴权问题；额外补充了完整旧源码对照、真实连接清理与前置 Origin 拒绝验证。所有操作在本地完成，尚未部署本轮性能优化。

## 发现与修正

### 中等：人口统计的地区键必须遵循数据库比较语义（已修复）

旧实现使用 `WHERE region='north'`，项目 MySQL 的 `utf8mb4_unicode_ci` 比较可能把 `NORTH`、`nórth` 或尾空格视为相等。原聚合按存储的地区字符串返回结果，再由 Python 字典查 `north`；Python 精确匹配可能漏计这些行，让真人数、供给与缺口计算发生偏差。

现在真人与虚拟玩家的两条聚合都用 SQL `CASE WHEN region=规范地区 THEN 规范地区 END` 生成分组键，比较继续交给数据库。没有使用 Python `lower()` 或修改存储数据。新增真实 MySQL 对照覆盖三种拼写，尾空格按数据库实际比较结果判断。当前完整计划、上限与缺口并发验证通过，仍是 2 条统计查询，含回填需求读取共 3 条。

修正版六种配置的 MySQL 基准：旧路径约 **85–93 ms**，新路径约 **8.4–8.8 ms**（预热后各 5 次配对中位数）。这是统计与规划路径的本地收益，不代表整个线上滚动任务耗时。

### 低：WebSocket 文档与补充测试范围（已补齐）

架构文档已更新为默认 12 条用户连接、稳定 30 秒才复位退避、当前关闭码和快速重试预算。新增测试保留真实消费者的 connect/disconnect、会话检查与 IP 中间件流程，只模拟 Redis/数据库基础设施，验证鉴权拒绝不注册用户连接槽、在线人数或频道组，IP 槽与心跳正确释放。另验证项目实际 Origin 校验链拒绝恶意和缺失 Origin。

鉴权终止后普通自动重试停止；在线统计在 `pagehide → pageshow` 时允许再尝试一次握手，这是既有页面恢复行为，不是无限重试。没有在本次复核中改变该行为。

### 疗伤独立对照：没有新增正确性发现

最初的查询复用测试共享提取后的领域执行段，能够验证复用与重新锁读的效果，但单独不能发现共享执行段同时被误改。因此额外从固定 Git 历史版本加载完整旧模块作独立对照，验证三种库存场景的全部数据库字段、返回统计与训练回调参数相等；同时用 AST 比较确认提取的治疗/扣药执行段与旧版本逐语句一致。测试在 SQLite 和 MySQL 均通过。

## 其他可优化机会

| 优先级 | 机会与实际证据 | 最小方案与必须保留的边界 |
|---|---|---|
| 1 | 资源结算重复读取粮食库存。真实 MySQL 的固定生产基准场景，50 个已有库存庄园发出 **100 次库存 SELECT**。 | 同一持锁结算调用栈复用已锁行，每个粮食发生增减的庄园可减少 1 次 SELECT。缺行创建、模板缺失、零粮删除、仓库权威账本、兼容 grain 字段、更新时间和回滚保持原样；不能挂成跨事务对象缓存。 |
| 2 | 竞技场技能查询按门客逐个执行。10 位门客发出 **10 次技能 SELECT**；先 prefetch 再调用当前序列化仍是 **10 次**，因为 `values_list()` 绕过缓存。 | 预取与序列化同时调整：只有已预取时从缓存读，否则沿原路径。锁后租用仍重新加载门客/技能；必须对照技能顺序、全部战斗快照和 SQL 数量，不能复用锁前快照。 |
| 3 | 资源事件仅合并同庄园写入。上述 50 庄园场景产生 **50 次事件 INSERT**。 | 在当前资源批次的同一个事务中收集事件，再批量插入；保留单庄园入口、事件顺序/时间戳与整批回滚。需实测优化后次数，不能只按理论承诺。 |
| 4 | 训练扫描逐门客包装单元素批量接口；每个成功门客还单独清除恢复记录，即使没有失败记录也发送 UPDATE。 | 小块批量初始化/成功键集合更新需要维持逐条失败隔离、此前成功已提交、计时起点、虚拟玩家写栅栏与提交后派发。不要预查失败记录存在性后跳过，避免遗漏并发新失败。 |

资源实测限定已有库存、发生粮食产出的场景，并用固定生产基准隔离账本读写；当前 1 庄园为 8 条 SQL，50 庄园为 253 条。它证明重复往返和事件写入次数，不是完整资源任务性能基准。建筑、科技、门客与兵力基准已有批量读取，不能把它们认定为尚存 N+1。
