## 已确认的问题

1. **实时通道频繁被拒绝。** 保留访问样本内，三个 WebSocket 端点合计 21472 次 403。当前 Web 日志独立记录 IP 容量拒绝 938 次、用户容量拒绝 235 次，因此不能将全部 403 都归为单一原因。Redis 缓存数据库 2 的有效 IP 连接数快照为 20、20、18、12、10、9、8、5、3；两个组达到配置的每 IP 20 上限，每用户上限为 12。

   远端聊天和通知脚本未包含本地已有的 `pagehide/pageshow` 释放及恢复处理；在线人数已有该处理。远端持续失败重连上限仍为 15 秒。每页面三个连接，多标签页、共享公网 IP 和页面生命周期均应调查。当前证据能解释实时更新异常，不能证明所有 HTML 页面卡顿都是此原因。另发现在线人数推送向已关闭协议发送数据的异常 1 次，应补齐关闭状态检查和消费组清理的并发测试。

2. **后台任务长尾。** 近 48 小时，竞技场虚拟储备培养 2886 次，平均 2.2524 秒、最长 147.406 秒、超过 10 秒 98 次；虚拟玩家维护扫描 2885 次，平均 4.3496 秒、最长 88.552 秒、超过 10 秒 173 次。当前维护 worker 曾采到约一个 CPU 核的占用。这些任务已在维护队列内，但仍共享 MySQL；未证明每次后台长任务都引起 HTTP 慢请求。

3. **数据库死锁有真实发生。** 招募 2 个、训练 1 个、虚拟维护完成协调 2 个任务因死锁重试；按任务 ID 在日志内部关联，5 个均随后成功。训练错误栈落在 `finalize_guest_training` 的锁定查询，招募落在候选人插入。当前训练查询 `select_for_update().select_related("manor", "template")` 可能扩大关联行锁范围，应核对 Manor → Guest 顺序及共享模板锁，而非去掉必要的锁。MySQL 全局统计和 digest 是从 9 月 20 日累计的，不能把累计 33919 次行锁等待当作近两天次数。

4. **上线切换导致短暂访问中断。** 样本内 51 次普通 HTTP 502 和 708 次 WebSocket 502 全部集中在 12:40–12:41，与本次单 Web 容器重建一致。代理日志为连接拒绝。新服务检查通过不能抹去切换期间的中断；当前已恢复。

5. **历史可观测性不足。** Caddy 使用 stdout JSON，Docker `20m × 5` 轮转，只保留约 2.5 小时的高频日志；Web 重建也丢失旧容器的访问记录。MySQL 慢查询日志未开启，阈值为 10 秒，无法有效定位亚秒级慢页面。现有记录不足以复盘任意玩家近两天的卡顿时间点。

## 建议的优化次序

1. **先修实时通道。** 复核并发布已有但未上线的前端生命周期改动，持续失败使用更长退避；评估多标签页共享连接或减少每页独立连接数，分别测试页面跳转、后退缓存、断网恢复和多标签页。保留 Origin、会话检查和连接容量保护，不简单放开所有限制。
2. **缩短后台长尾并治理锁。** 对虚拟维护、竞技场储备培养采集 SQL/CPU/锁耗时，缩小现有批次、设置每轮耗时预算，利用原有幂等状态和续跑机制分批推进；统一招募、训练与页面写操作的锁顺序，只锁必须写入的行。不得为缩短耗时跳过资产校验或重复发放保护。
3. **补日志和指标。** 保留至少 48 小时的访问指标与错误样本，长期聚合按端点 P95/P99、5xx、WS 拒绝原因、队列等待及任务执行时间，敏感信息脱敏；减少高频正常日志占用。慢 SQL 观察应单独限定阈值、采样和日志磁盘上限，先看新增期间的增量，避免拿累计 digest 推断两天结论。
4. **改上线流程。** 使用候选 Web 先启动、健康通过后切换代理、旧连接排空再退出的发布方式，提前验证多实例下会话及 Redis 连接配额逻辑，消除单容器重建的 502 窗口。
5. **定点优化页面。** 招募刷新先查无到期工作是否快速返回、合并重复模板/技能读取；竞技场报名先补锁等待、快照、提交和入队阶段计时，再决定最小修改。当前地图搜索延迟较低，暂不再次大改搜索实现。

本轮只读取运行状态及记录诊断文件，没有修改生产配置、玩家数据或重启服务。
