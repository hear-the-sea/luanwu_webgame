## 处理方向

1. **优先观察并隔离持久化压力。** 补数据盘读写延迟、fsync、Redis 客户端延迟的短周期监控，定位实际慢点；缓存、会话校验及连接状态与持久化任务 broker 分 Redis 实例，避免易变缓存写入与任务持久化互相影响。迁移要验证 TTL、会话权威状态、连接配额及 worker/broker 一致性，不能把整个 Redis 的 AOF 直接关闭，否则存在待执行任务丢失风险。
2. **给 Web 增加合理内存余量并观察增长。** 当前逼近 384MiB，可考虑单独配置变更提高余量；同时采集进程 RSS、活跃连接、线程及请求趋势，确认是稳定缓存/分配器保留还是持续增长。不要只靠反复重启缓解。
3. **上线已验证的生命周期与培养软预算修复。** 这能降低无用重试及长任务占用，但需要保留已经上线的疗伤和其他版本改动；不应宣称上线这些代码即可消除持久化抖动。
4. **进一步缩小后台写入长尾。** 针对新发现的虚拟玩家轮换 227 秒，检查是否按完整幂等步骤分批，并关联写入量与 fsync 延迟；维护安全记录不能随意中断。

目前不需要以“CPU 不够”作为默认升级理由。优先级应落在持久化超时、Web 内存余量以及仍未上线的实时连接修复。
