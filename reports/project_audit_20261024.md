## 发现

### A01 · P1 · 注册页面泄露有效邮箱激活令牌

- 位置：`accounts/views.py:502,535,759,828`；`templates/accounts/email_verification_pending.html:31`。
- 证据：注册生成的邮箱验证令牌同时以 `resend_token` 返回页面，写入隐藏表单字段；重发响应也返回新的有效验证令牌。隐藏字段对浏览器用户可见。
- 触发：注册一个尚未占用的邮箱，从响应提取 token，直接向验证入口 POST，即可设置 `email_verified=True`、`is_active=True` 并登录，无须读取邮箱。
- 影响：邮箱所有权验证失效，可使用自己不控制的邮箱创建已验证账号。此结论不等于可接管已存在的已验证账号。
- 验证：隔离测试已直接复现注册响应 → 提取凭据 → 激活并登录。
- 最小修复：激活令牌仅经邮件交付；重发使用会话绑定或独立 salt、独立用途的凭据。激活端不得接受重发凭据。
- 修复验收：注册、重发响应中全部可见凭据均不能完成激活；邮件中的真正令牌仍可正常激活。

### A02 · P2 · 已有 WebSocket 连接不能识别账号禁用、改密和会话过期

- 位置：`websocket/consumers/session_guard.py:58-89,94-95,423`。
- 证据：校验使用连接建立时的 `scope.user`、已加载的 session 内容、session key 存在性和单会话记录，没有重新验证账号状态、密码对应的 session auth hash 和有效期。数据库 session 行存在不等于会话未过期。
- 触发：在连接建立后禁用用户、改变密码，或使 session 的 `expire_date` 过期。
- 影响：原连接仍通过校验，世界聊天与通知的撤销边界不完整；重复执行当前校验也不能发现上述变化。
- 验证：上述三种场景分别在隔离测试中复现，校验均错误返回 True。
- 最小修复：定期重载有效 session，并重新认证当前用户、有效期及 auth hash；保留现有单会话校验和短期缓存。
- 修复验收：三种撤销场景在校验周期内关闭连接；正常连接、重登录踢旧连接及基础设施故障策略继续有效。

### A03 · 安全依赖欠账 · Django 固定版本缺少后续安全补丁

- 位置：`requirements.lock.txt:18`、`requirements-dev.lock.txt:23`，均为 `Django==5.2.8`；当前系统 Python 安装版本也是 5.2.8。`Dockerfile` 使用运行时 lock 文件安装依赖。
- 官方证据：Django 已于 2026-10-06 发布同一 LTS 分支的 5.2.18 安全版本，包含 HTTP 头解析拒绝服务等修复；此前 5.2.13 还修复了 ASGI 内存限制绕过等问题。
- 影响边界：确认缺失安全补丁；没有证明每项公告中的 CVE 都能从本项目触发。生产 Caddy 的请求体上限可缓解部分路径，不能替代框架升级。
- 建议：在 5.2 分支升级至包含已发布安全修复的版本，重新生成生产与开发锁文件，执行账号、ASGI、后台和数据库回归；本次没有修改依赖。
- 来源：[2026-10-06 官方安全公告](https://www.djangoproject.com/weblog/2026/oct/06/security-releases/)、[2026-04-07 官方安全公告](https://www.djangoproject.com/weblog/2026/apr/07/security-releases/)。

### A04 · P2 · 钱庄已经扣款发货，展示失败却被报告为兑换失败

- 位置：`trade/services/bank_flows.py:20-28,39-47`；`trade/view_helpers.py:263-272`。
- 证据：扣银、发金条、写兑换日志的事务先提交，随后构造返回值，再以 `fail_closed=True` 查询“下一根汇率”。这次缓存/数据库查询失败会使整个服务调用抛错，视图将结果当作失败。
- 影响：用户看到失败后重试，会再次购买；首笔交易已实际生效。
- 验证：隔离事务中注入下一次汇率不可用，服务抛 `GoldBarPricingUnavailableError`，但银两从 1,000,000,000 减至 999,999,900，金条增加 1，兑换日志已存在。
- 最小修复：返回已提交交易的确定结果；把下一次汇率作为可降级的展示字段，其查询失败不能覆盖交易成功。重试安全性可通过业务幂等凭据进一步保证。
- 修复验收：提交后展示查询故障仍返回成功，首笔扣款与金条数量准确；提交前故障仍能完整回滚。

### A05 · P2 · 普通邮件附件缺少物品模板时被永久跳过

- 位置：`gameplay/services/utils/messages.py:520-522,543-545,572-583`。
- 证据：缺失绑定物品模板会抛错，但缺失普通物品模板直接 `continue`，之后仍把邮件标记为已领取并取消删除保护。
- 触发：历史邮件中的模板被移除、漏同步，或运营脚本发放尚未加载的物品；内部邮件创建路径不保证模板已存在。
- 影响：相应奖励未发放，却不能再次领取；后续补回模板也不能恢复。
- 验证：缺失普通道具 3 个的邮件领取结果为空且 `is_claimed=True`；创建模板后再次领取报已领取。
- 最小修复：发奖前统一校验普通和绑定道具模板，缺失时回滚并保留未领取状态，复用当前绑定附件的处理方式。
- 修复验收：混合资源/普通道具/绑定道具缺失时不发生部分入账；补回模板后能一次性领取。

### A06 · P2 · 帮会与庄园锁顺序存在循环等待

- 位置：`guilds/services/contribution.py:80-88`；`guilds/services/member.py:225-231,262-277`；`gameplay/services/resources.py:655`。
- 证据：捐献先锁 Manor 再锁 Guild；退帮、踢人先锁 Guild/Member，再结算资源并锁 Manor。解散和部分产出科技升级同样存在 Guild → Manor 路径。
- 触发时序：捐献事务持有玩家 Manor 等待 Guild；退帮事务持有同一 Guild 等待该玩家 Manor，形成环。
- 影响：MySQL 会选择回滚一个事务；当前同步入口没有相应死锁重试，可能出现操作失败和长尾延迟。未证明会产生重复奖励或永久资产损坏。
- 验证状态：已追踪到实际获取锁的调用链；未在真实 MySQL 中复现。
- 最小修复：统一跨帮会/庄园的获取顺序，集中管理获取锁的边界；注意 `select_related` 联表锁的范围。不能只改注释或仅给失败入口加重试。
- 修复验收：真实 MySQL 中验证捐献与退帮、踢人、解散、产出科技升级的并发矩阵。

### A07 · P2 · 擂台在全局锁事务内运行整场战斗

- 位置：`gameplay/services/arena/ring.py:68-78,101-102,179-200`。
- 证据：每次擂台操作锁两个擂台、当前任期和全部现任擂主的 Manor；挑战在同一事务中执行完整 `simulate_report()`。
- 影响：一次慢战斗不仅阻塞本擂台，还会让另一个擂台操作及两名擂主需要庄园行锁的普通玩法等待。锁范围和模拟位置明确，实际阻塞时间未量化。
- 最小修复方向：事务内固定输入与版本，事务外模拟，短事务校验版本后提交；须保留跨台占据限制及 action token 幂等，不能简单移走锁。
- 修复验收：真实 MySQL 验证跨擂台并发、重复提交、版本变化以及擂主其他玩法延迟。

### A08 · P2 · 日志清理吞吐小于合理运行规模下的生成量

- 位置：`gameplay/tasks/maintenance.py:37,51-69,98`；`config/settings/celery_conf.py:400-402`；`gameplay/tasks/resources.py:36-48`。
- 证据：每小时仅对 ResourceEvent 删除一批、最多 500 条；资源同步每分钟运行一次，默认最多处理 500 个庄园，并对非零资源分别写流水。
- 触发：持续产生超过 500 条流水/小时，即平均超过约 8.33 条/分钟。
- 影响：过期流水净增长，15 天保留目标不能长期兑现，逐渐增加存储与查询成本。是否已有生产积压尚未读取数据验证。
- 补充：ResourceEvent 和 BattleReport 的现有时间索引以 manor 为前导，而全局清理按 created_at 筛选排序；需 MySQL EXPLAIN 确认扫描代价。
- 最小修复：按时间预算执行多批小事务，可配置吞吐并监控最老过期记录、积压数量；根据执行计划补索引。不要改成一个无限长删除事务。
- 修复验收：模拟超过当前清理能力的稳定写入，证明积压可追平，验证删除保护与索引计划。

### A09 · P2 · 全站打工结算一次性加载并锁定全部到期记录

- 位置：`gameplay/services/work.py:142-171,188-201`；`config/settings/celery_conf.py:312-314`。
- 证据：后台每分钟调用全站完成逻辑，使用无 limit 的 `list(select_for_update().filter(...).select_related('guest'))`，在一个事务内更新所有任务与相关门客，没有分批或 skip_locked。
- 触发：服务中断后积压、集中到期或玩家数量增长。
- 影响：内存和锁持有量随积压增长，阻塞玩家的门客操作和召回。此项针对全站任务；单庄园刷新受玩法人数上限约束。
- 最小修复：统一锁顺序后，按 `(complete_at,id)` 有界取批、逐批提交，保留状态条件保证幂等。
- 修复验收：大积压下测内存、事务时长和并发玩家操作；确保不会提前释放仍被其他活动占用的门客。

### A10 · P2 · 列表为获取战报链接而读取完整战报大 JSON

- 位置：`gameplay/services/utils/messages.py:373`；`gameplay/views/messages.py:301`；`gameplay/selectors/arena/rings.py:213-214`。
- 证据：消息列表与跳转、每页 30 场的擂台详情查询均 join 完整 BattleReport，相关模板仅需要战报 ID。BattleReport 含 11 个 JSONField，包括 rounds 和双方队伍。
- 影响：产生不必要的数据读取、传输和 JSON 反序列化。实际收益取决于真实战报大小，未实测线上延迟。
- 最小修复：去掉这些查询中的 `select_related('battle_report')`，继续直接使用 `battle_report_id`；保留实际需要的玩家预加载。
- 修复验收：链接与访问控制保持一致，确认 SQL 选择列减少，使用大体积战报比较耗时和内存。

### A11 · P2 · 免费侦察重复存储整份阵容，缺少保留清理

- 位置：`gameplay/services/arena/ring.py:129-140,226`；`gameplay/selectors/arena/rings.py:228-234`。
- 证据：同一玩家对同一任期版本使用新 token 会新建一份 lineup 快照和 action；重复 token 有幂等保护，但不同 token 不复用相同版本快照。24 小时后的页面隐藏不等于删除，未发现对应表的定时保留清理路径。
- 影响：按现有每账号 20 次/分钟的接口限流，理论上单账号每天可请求 28,800 份快照；这是上限计算，不是线上观测。长期增长会扩大数据库和备份体积。
- 最小修复：复用 buyer/tenure/version 对应快照，设计快照和幂等凭据保留期，清理时保护仍有效的引用。
- 修复验收：不同 token 的同版本侦察复用数据，过期记录按策略清理，不影响有效凭据重放。

### A12 · 潜在 P2 · 多名额拍卖未满额时可接受低于起拍价的报价

- 位置：`trade/services/auction/bidding.py:236-264`；`trade/services/auction/rounds_settlement_support.py:101-108`。
- 证据：仅在排名为空时检查起拍价；已有出价但尚未满额时，新竞拍者可报任意合法正整数。结算使用最后一名中标者报价作为所有中标者的支付价。
- 复现：起拍价 100、名额 2，已有 100 的报价时，第二名报价 1 被真实 `validate_bid_amount()` 接受；当前结算规则将统一按 1 成交。
- 当前配置限制：`data/auction_items.yaml` 全部为单名额、起拍价 1，默认配置不触发。不能据此断言当前线上正在被低价利用。
- 最小修复：所有报价先统一验证不低于起拍价，再应用加价规则。
- 修复验收：覆盖多名额未满、已满、已有报价者加价及单名额场景。

## 边界与修复方向

现有代码大多已有资源和库存集中写入口、事务、锁 token、失败降级和分批扫描；这些机制值得保留。主要缺口集中在凭据用途混用、WebSocket 权限重新校验、交易提交后的错误语义、缺失模板的发奖行为、跨服务锁顺序，以及少数任务和列表的容量边界。

建议修复顺序：A01 → A02/A03 → A04/A05/A06 → A07/A08/A09/A10/A11 → A12。A10 可低成本单独修复，不必等待其他性能改造。

范围判断：账号、交易和发奖问题采用局部修复（Surgical Fix）；锁序和擂台模拟需要明确事务所有者并做局部结构调整（Structural Shift）。没有足够证据支持整体架构迁移或大范围重写。

额外加固与文档：后台 `/admin/login/` 未复用普通登录的账号/IP 失败锁策略，仓库 Caddy 也未定义后台专属入口限制；应结合实际部署的访问控制核查。`docs/arena_ring.md` 仍描述付费侦察及奖励，与当前测试规定的免费、无奖励行为不同，应更新文档，不能把现行明确行为误报为漏洞。

仍需验证：目标 MySQL/Redis 的并发门禁、真实 Celery 队列故障恢复、线上查询执行计划与战报体积、日志实际积压和生产入口访问控制。本报告既不宣称不存在其他漏洞，也不把静态热点表述成已发生的生产事故。
