# 虚拟玩家培养动作优化路线图（2026-08-12）

> 文档性质：V2 虚拟玩家日常培养的优化决策、实施顺序和验收口径。
>
> 适用范围：普通日常培养、独立虚拟招募、建筑/科技发展和培养调度。竞技场补位继续使用独立的目标驱动流程，不把竞技场瞬时培养规则混入普通日常周期。
>
> 版本策略：本路线图面向当前 V2 主路径，不为旧 V1 运行时保留兼容分支。历史数据若不能满足 V2 契约，应在迁移或 preflight 阶段显式修复、隔离或 fail-closed，不能静默回退旧执行器。

## 1. 决策摘要

当前动作流程的持久化、并发和恢复骨架是合理的，暂不推翻。需要优先调整的是“候选选择前的目标/阻塞判断”以及“资源不足后的有界等待策略”。性能优化以减少无效候选、数据库往返和重复唤醒为目标，不以牺牲锁内复核和幂等边界为代价：

1. 建筑/科技是周期内的最低保障动作，但资源不足时不能继续回退到同一瓶颈资源的低收益消耗动作；可证明能缩短恢复时间的经济投资仍可执行。
2. 门客容量扩张必须由明确的门客数量目标驱动；门客数量目标未满足时优先升级聚贤庄，容量满足后才进入质量培养。独立日常招募仍然运行，不占普通培养槽位，也不成为普通周期阶段。
3. 候选生成改为分阶段、按需生成。优先组没有可执行候选时，才构造质量组和回退组；同一批次共享只读快照和固定 catalog，禁止按候选产生 ORM 往返。
4. `no_action` 要按阶段、阻塞类型和前置 housekeeping 分维度统计，区分真正没有进展、资源等待、队列占用、锁冲突和 housekeeping，不能用一个总数判断策略质量。
5. 资源等待、候选状态和唤醒必须有界，不能让周期永久开放或因固定短重试形成热循环。
6. 业务策略稳定后，再拆分维护服务的职责；不能用大量薄包装函数把一个大模块换成多个难以追踪的中转层。

## 2. 当前基线与问题证据

本路线图基于 2026-08-12 完成的 8 名新 V2 虚拟玩家、15 天逻辑回放，以及当前工作区代码审计。回放用于验证业务策略，不作为线上请求延迟或生产吞吐的直接证明。

| 指标 | 当前结果 | 判断 |
|---|---:|---|
| 基线模拟玩家 | 8 名，档案 ID 701～708 | 样本足以发现策略问题，不足以完成全量校准 |
| 逻辑事件 | 14,517 | 逐事件串行回放，耗时主要来自验证驱动 |
| 培养调用 | 5,827 次 | 每次都经过完整规划、评估和事务路径 |
| 培养尝试 | 7,810 次 | `applied` 6,989 次，`no_action` 821 次 |
| 当前 `no_action` 比例 | 10.5% | 已明显低于旧方案约 48.6% |
| housekeeping 原因 | 577 次 | `salary_already_paid`、`no_guests_to_heal`，不应计为策略失败 |
| 建筑升级 | 316 次 | 8 名玩家均累计达到至少 2 次 |
| 科技升级 | 48 次 | 8 名玩家均累计达到至少 2 次，但周期内覆盖不足 |
| 招募完成 | 965 次，全部完成 | 940 次为满员后的正常候选尝试 |
| 最终门客数 | 每人 4 名 | 聚贤庄均为 1 级，容量阶段仍未真正启动 |

最重要的瓶颈不是旧预算或强度限制，而是真实资源不足：

- 完成周期共 335 个，其中约 219 个周期未完成至少 2 次建筑升级，约 332 个周期未完成至少 2 次科技升级。
- 科技候选因 `insufficient_resource` 被拒绝约 5,028 次。
- 建筑候选因 `insufficient_resource` 被拒绝约 2,765 次。
- 当前选择器在优先候选被资源拒绝后，仍可能进入普通回退组，继续执行征兵或其他资源动作，造成资源瓶颈被放大。

因此，当前问题的性质是“资源状态没有形成决策阶段”，不是单纯的候选排序问题。

## 3. 当前动作流程评估

### 3.1 应保留的流程

以下机制属于正确的稳定性边界，不因简化而删除：

- due 扫描、批量预加载和有界选取，避免为每个 Profile 创建大量独立定时任务。
- `BotMaintenanceCycle` 持久化周期、槽位、间隔种子、动作状态和重试时间，保证重启、重复扫描和 claim takeover 不会重新抽样。
- 规划阶段生成 `MaintenancePlan`，执行阶段在锁内重新读取并验证资源、队列、门客和策略快照。
- `BotProfile → Manor → Guest` 的稳定加锁顺序，以及资源、工资、领域完成和外部对账的幂等边界。
- 建筑、科技、训练完成事件对账；完成事件只能推进其所属周期，不能因为重复事件重复消耗槽位。
- 普通虚拟招募使用独立配额、卡池快照和 `GuestRecruitment(source=virtual)`，不占 16 个普通培养槽位，不推进 `next_growth_at`；每日首个招募触发后，一次性结算当天的配额快照：声望低于 10,000 时只有 3 次乡试和 3 次村募，共 6 个池位，明确不生成殿选；声望达到 10,000 后从下一个自然日恢复殿选、乡试、村募各 3 次，共 9 个池位。逐池直接扣除该档位银两并即时入册，不创建新的虚拟 pending 队列或完成任务。
- 竞技场补位使用单独目标、战力投影和瞬时动作规则，不由普通日常培养“顺便完成”。

### 3.2 需要调整的流程

当前 `maintenance.py` 的主路径大致是：

```text
due 扫描
  → 批量预加载快照
  → 打开/恢复周期
  → 工资、产出、治疗前置动作
  → 先生成当前优先组的候选并做资源、强度、队列和类型评估
  → 只有当前组没有可执行动作时，才按需生成后续候选组
  → 按候选组选择
  → 锁内重验证并执行
  → 写入尝试/周期审计
  → 等待领域完成或下一槽位
```

骨架没有问题，但候选生成和回退决策过早混在一起：

- 规划器需要为每个槽位构造较多实际上不会被选择的候选。
- 资源不足、队列占用、策略限制在选择器中都表现为“候选不可用”，但业务回退语义不同。
- 计划阶段和锁内重验证阶段会重复走较大部分候选逻辑。
- 周期动作计数、覆盖集合和历史高价动作字段存在部分重复的状态表达。

目标是把流程改成“目标/阻塞判断 → 最小候选集 → 锁内复核 → 执行 → 有界唤醒”，而不是继续堆叠候选排序规则。

性能原则：一次维护调用只允许读取一次可复用的只读快照；候选 builder 只能消费快照和固定配置；锁内只重读执行所需的最小领域状态。候选数量、查询数量、锁等待和唤醒次数都必须进入基准，不允许用“代码更短”替代性能证据。

## 4. 不可破坏的业务不变量

后续优化必须继续满足以下约束：

1. 普通周期最多 16 个动作槽位，只有真正提交的动作占用槽位；可重试资源等待、锁冲突和候选评估失败不能伪造成功动作。
2. 建筑/科技各 2 次是周期最低覆盖目标，不是无条件成功承诺。规划器在存在对应目标且周期仍有槽位时优先完成候选评估和提交尝试；资源、队列或策略阻塞时必须记录阻塞原因并有界退出，不能把阻塞评估计为成功提交。
3. 建筑和科技的正常动作仍走正式 quote、资源扣除、倒计时和完成对账；不使用竞技场免费补贴。
4. 每日虚拟招募独立于普通培养周期；低于 10,000 声望时当天不生成 3 次殿选，达到目标后次日恢复，配额快照不会因普通周期动作失败或同日声望变化而重复补发。
5. 满员招募只能在候选稀有度更高、战力不下降、门客空闲且替换后的实际工资可承担时替换；否则由独立招募流程保留候选记录，不强制删除门客，也不占普通培养槽位。
6. 资源不足必须是真实资源不足，不得通过虚假声望、免费资源或绕过领域服务来“完成”动作。
7. 读路径只读取和构造快照，不能隐式写入 Profile、周期或领域对象；所有写入由维护服务、招募服务和完成对账服务负责。
8. 普通培养和竞技场补位的动作类型、资源语义、强度治理和幂等凭证必须保持隔离。
9. 普通 V2 的维护执行不设置 `strength_cap`；参考快照只用于画像、目标选择和审计，不参与培养动作拦截。资源、工资、队列、领域合法性和单次跨越最多一个声望段仍然是有效约束。

## 5. 短期计划：策略修正（P0）

短期目标是先修正业务结果，不做大规模文件移动。每一步都应配套窄范围测试和 3～15 天回放。

本轮已落地的 P0 基线：普通门客目标已持久化并完成历史回填；普通周期的建筑/科技覆盖欠账会跨周期承接并在成功动作后递减；资源等待最多重试 6 次，超限关闭周期并进入下一周期；独立日常招募改为每日整批即时结算，逐池独立扣费，银两不足或最终阵容校验失败的池位不写入配额审计、下次唤醒重试，其余池位继续；选择器对资源阻断优先组不再无条件回退；超量 due backlog 改为记录溢出并继续选择公平的有界批次。候选按需生成已在普通 scheduled V2 主路径做最小范围落地，细粒度候选组指标和评分校准仍属于后续 P1。

2026-08-13 增量优化：周期 schema 3 新增 `action_attempt_counts`，将建筑/科技候选评估与成功提交分开；最低评估目标按剩余缺口动态轮转，失败评估不会继续放大成功欠账或永久压制另一类型。资源快照从真实 RecruitmentPool 价格计算每日招募现金流，并只用于 24/72 小时预测和净可支付时间，不改变 `spendable_resources`，不预留、不预扣，也不改变招募服务的逐池收费顺序。经济恢复补入同时产粮和银两的茅厕，银库只在银两接近容量时优先；藏宝阁不再被错误当作银两容量建筑。报表分类新增 `progress_applied`、`progress_blocked`、`resource_wait`、`domain_wait`、`lock_retry`、`housekeeping`、`scheduler_wait` 与 `candidate_exhausted`。

### 2026-08-13 本轮实施验收

- 使用隔离 SQLite 数据库，对 8 名新 V2 玩家进行 15 个逻辑日的 faithful replay；玩家 ID 为 33～40，回放无业务异常。
- 每名玩家每日按声望门槛生成 6 个招募池位；15 天共完成 720 次付费招募批次，未改变招募服务的逐池扣费和即时入册语义。
- 结束时 8 名玩家均保持 active，共 32 名门客（平均 4 名）；建筑累计等级 550，科技累计等级 35，门客等级总和 1,489；银两总量 26,789，粮食总量 1,104,817。
- 定向维护、资源、招募、并发、架构门禁和玩家提示测试：285 passed, 12 skipped；`compileall` 与 `git diff --check` 通过。
- 全量测试首次发现的 2 个本轮新增玩家提示问题已修复并由定向回归覆盖。剩余 5 个失败属于既有审计证据过期：旧审计文档行数、D1 清单引用已删除测试文件、Gate E 缺少阶段指标、以及 manifest 仍记录旧的节点数；它们不属于本轮维护逻辑回归，后续应单独刷新证据，不在本轮策略改动中混修。

### 2026-08-13 虚拟资产用途收敛

- V2 虚拟玩家的家丁数量固定为 0；虚拟护院候选直接使用银两/粮食报价，不读取或消耗家丁库存，人员粮耗也按 0 家丁计算。
- 新建 V2 玩家仍物化完整建筑/科技目录以满足锁定 catalog 合约，但无运行时用途的建筑等级固定为 1、科技等级固定为 0，不进入发展候选。
- 虚拟建筑候选只允许农田、税务司、澡堂、茅厕、粮仓、银库、聚贤庄、酒馆和祠堂：分别对应资源产出、容量、门客容量、候选抽取或虚拟动作缩时。
- 虚拟科技候选保留建筑学、农耕，以及发展画像实际兵种类别对应的兵种科技；侦查、行军、养殖、冶炼、锻造和未使用兵种科技不再升级。
- 存量 V2 玩家通过迁移 `0180_zero_v2_virtual_player_retainers` 将 `Manor.retainer_count` 一次性归零；本工作区只创建迁移文件，未在当前数据库执行迁移。迁移应用后，既有 V2 数据与新建玩家遵守同一契约。

### P0-1：资源不足时进入有界资源等待

当前已修正：建筑/科技优先组的候选全部因 `insufficient_resource` 或工资保护而不可执行时，选择器保留资源阻塞结果，不再无条件从普通回退组选择征兵或库存动作；队列占用、策略限制等非资源阻塞仍按既定回退规则处理。

目标规则不是“禁止所有同资源动作”，而是禁止不能改善瓶颈的低收益消耗。资源策略需要同时看资源成本向量、预计自然恢复时间、恢复动作的边际产出和动作完成时间：

```text
优先建筑/科技候选
  ├─ 队列占用：寻找同一目标组中另一个未占用的建筑/科技
  │    ├─ 仍有可执行目标：继续提交当前目标组
  │    └─ 全部占用：记录 queue_wait，等待领域完成；无资源瓶颈时才按需生成质量组
  ├─ 资源不足：记录 resource_wait，计算瓶颈和预计恢复时间
  │    ├─ 有可支付且有正向回本预期的恢复投资：只评估恢复候选
  │    ├─ 没有可支付恢复投资：等待自然产出，不执行同瓶颈低收益消耗
  │    └─ 等待超过上限：关闭当前周期并把目标结转到下一周期
  └─ 策略或领域限制：记录原因后按类型偏好回退
```

具体要求：

- 把“队列不可用”和“资源不可支付”建模为不同的决策分支。
- 资源不足时，普通回退不得选择会放大同一瓶颈且不能改善恢复时间的征兵、库存或其他银粮动作；与瓶颈无关且不影响最低覆盖的动作可以按策略继续。
- 经济恢复建筑也必须经过正常 quote、资源评估和锁内重验证；不能因为处于恢复状态而免费升级。恢复候选必须记录 `resource_cost`、`production_delta`、`payback_seconds` 和目标动作的 `next_affordable_at`。
- 工资结算、普通动作和独立招募在策略上是三个预算维度，但最终都消耗同一个 `Manor.silver`；不能把它们描述成三个物理银两账户。普通 V2 不再用未来工资预留作为全局硬门槛，独立招募仍按自己的日配额直接消费真实银两，余额不足时延期且不消耗配额；建筑/科技与低优先级动作则由周期优先级统一仲裁。
- `resource_wait` 使用有界退避：优先唤醒时间为 `next_affordable_at`，再叠加策略配置的最小/最大退避；当前实现复用 `BotMaintenanceCycle.next_decision_at`，并在 payload 记录 `next_resource_check_at`。连续等待达到 6 次后标记 `deferred_to_next_cycle` 并关闭当前周期，避免永久 open。
- 等待期间不重复生成质量组和回退组，不重复执行完整 ORM 规划；只在资源结算边沿或 `next_resource_check_at` 到期时唤醒。
- `no_action` 统计中将 `resource_wait`、`deferred_to_next_cycle` 与真正 `candidate_exhausted` 分开。

验收：

- 当科技因银两不足被拒绝时，同一槽位后续不能提交征兵或库存消耗动作。
- 银两恢复后，科技优先级可以重新获得候选，不需要人工重置周期。
- 恢复建筑只有在真实 quote 可支付且预期恢复收益满足策略阈值时才可提交；不能因为“恢复阶段”绕过资源约束。
- 持续资源不足时周期不会永久开放，重试次数、等待时间和结转结果可审计。
- 资源不足不会导致周期动作计数虚增、招募配额丢失或声望伪增长。

### P0-2：增加容量扩张阶段

容量扩张是普通培养的一个目标，不是招募替换阶段。目标来源必须在周期快照中冻结：

- 普通培养：读取 `BotProfile.guest_count_target`，该值由启动画像计算并在迁移 `0178` 中为历史 V2 玩家回填，再复制到周期 payload 作为冻结快照；没有该目标时不升级聚贤庄。
- 竞技场补位：只读取竞技场目标的 `critical_guest_count`，仍由竞技场独立流程推进。
- 同时存在多个目标时，普通周期只使用普通目标；竞技场目标不得偷偷改变普通周期的资源和槽位语义。

普通培养目标阶段：

```text
capacity_expansion
  → capacity_stable
  → quality_development
```

规则：

- 当冻结的普通门客数量目标超过当前容量时，优先升级聚贤庄；目标缺口超过容量时才进入 `capacity_expansion`。
- 每次最多启动一级，等待建筑完成后重新计算容量，不连续虚拟升满。
- 独立日常招募不暂停，继续使用自己的配额、候选池和替换规则；每日首个触发一次性处理配额快照中的 6 或 9 个计划池位，每个可支付池位最多产出一个最终候选，统一按稀有度/战力排序后应用容量与替换规则；它不成为 `BotMaintenanceCycle` 的阶段，也不消耗普通 16 槽位。殿选开关在每日快照中冻结，跨过 10,000 声望不会在当天追补。
- 容量达到目标后，不再把聚贤庄作为普通高频候选；进入建筑/科技和门客质量培养。
- 容量升级的资源不足由 `resource_wait` 作为阻塞状态处理，不与容量目标互相覆盖；资源恢复投资是否优先由回本时间和目标缺口共同决定。

验收：

- 容量不足时，周期审计能看到 `capacity_expansion` 原因和聚贤庄动作。
- 普通画像无门客数量目标时，聚贤庄不会因随机建筑偏好连续升级。
- 容量达标后，聚贤庄不再抢占建筑优先级。
- 满员后的独立招募仍能尝试更高稀有度替换，且不会改变普通周期的阶段、槽位或 `next_growth_at`。
- 即时招募的每个已支付池位都保留一条 completed `GuestRecruitment` 审计记录，`duration_seconds=0`；不再为新虚拟招募调度 Celery 完成回调。历史 pending 记录仍由既有完成函数负责收尾，不作为新路径的生产契约。

### P0-3：区分“尝试”与“成功完成”

每周期的建筑/科技最低覆盖指标不再只使用一个“尝试次数”。建议拆成以下层级：

| 层级 | 含义 |
|---|---|
| 候选生成 | 为当前目标组构造了候选；未生成的后续组不计为阻塞 |
| 候选评估 | 规划器确实以建筑/科技为当前优先目标完成资源、队列和策略评估 |
| 提交尝试 | 进入锁内 quote/复核/执行路径，成功或失败都可审计 |
| 提交成功 | 通过资源、队列和锁内复核，正式启动升级并占用槽位 |
| 完成生效 | 领域完成事件已对账，等级实际增加 |

周期 payload 和指标应按 `phase/objective/action_kind/stage/reason` 聚合。`covered_action_kinds` 从成功提交计数派生，避免双写；同时保留每类首个阻塞原因、累计阻塞数、最近一次重试时间和未评估原因。

当前 schema 3 已以 `action_attempt_counts` 持久化最低目标的候选评估次数，以 `action_kind_counts` 保留成功提交次数，并继续由领域完成事件表达最终生效。`candidate_evaluated` 可以满足“尝试覆盖”统计，但不能计入 `submission_count` 或 `completion_count`。资源或队列长期阻塞时，指标应显示“目标存在但未提交”，而不是伪造 2/2 成功。

### P0-4：拆分 housekeeping 统计

以下结果不应直接与培养失败合并：

- `salary_already_paid`
- `no_guests_to_heal`

保留底层尝试记录，并增加 `stage=preamble|slot|recruitment` 维度，报表拆成：

- `progress_applied`
- `progress_blocked`
- `resource_wait`
- `domain_wait`
- `lock_retry`
- `housekeeping`
- `candidate_exhausted`

当前回放中 housekeeping 占所有 no-action 的约 70%，拆分后才能准确观察真正的策略阻塞率；如果一次调用先完成 housekeeping、随后又发生培养阻塞，不能只按最后一个 reason 覆盖整次调用。当前已提供稳定的进度分类器，底层尝试继续保留原始 outcome/reason；后续报表应按尝试 stage 调用分类器聚合，而不是覆盖原始审计。

## 6. 中期计划：阶段化规划与性能优化（P1）

中期目标是让规划器只为当前目标生成必要候选，并让资源、队列和生命周期画像进入同一套可解释策略。性能目标是减少无效候选和数据库往返，而不是减少必要的锁内复核。

### P1-1：引入目标/阻塞状态，而不是单一线性阶段

资源恢复和容量扩张可能同时存在，不能用一个互斥的线性阶段表达所有状态。建议持久化“培养目标”和“阻塞状态”两个维度：

| 培养目标 | 进入条件 | 主要动作 | 离开条件 |
|---|---|---|---|
| `capacity_expansion` | 普通门客数量目标超过当前容量 | 聚贤庄逐级升级 | 容量达到目标 |
| `infrastructure_coverage` | 建筑/科技仍未达到周期最低覆盖 | 建筑、科技和必要经济恢复 | 覆盖完成、目标完成或有界结转 |
| `quality_development` | 容量稳定且基础设施覆盖完成 | 训练、装备、技能、库存 | 当前周期目标覆盖完成 |
| `idle` | 没有合法动作但存在未来唤醒点 | 等待资源、领域完成或下一周期 | 唤醒条件满足 |

阻塞状态使用独立枚举：`none`、`resource_wait`、`queue_wait`、`domain_wait`、`lock_retry`、`deferred_to_next_cycle`。`roster_replacement` 不属于普通培养周期，由独立招募服务维护。

状态实现要求：

- 不新增与 `current_action_state`、`next_slot_due_at`、`next_decision_at`、`last_reason` 重复的事实来源。
- 如果短期仍使用 `payload`，必须带 `state_schema_version`、普通门客目标、覆盖欠账、进入时间、阻塞原因和 `next_wakeup_at`；当前周期使用 schema 3、`ordinary_guest_count_target`、`action_attempt_counts`、`action_kind_counts`、`coverage_debt`、`next_resource_check_at` 和有限长度历史，并对计数、欠账和唤醒载荷做严格边界校验。
- 状态转换必须写入周期审计并参与计划 digest；重启和重复扫描只能恢复已有状态，不能重新抽样或跳过阻塞。
- 资源等待和队列等待只更新阻塞维度，不反复重建目标阶段。

### P1-2：候选按需生成（lazy candidate pipeline）

将候选生成分为三层，并把“快照读取”和“候选生成”分开：

1. `priority_candidates`：建筑、科技、容量扩张和经济恢复。
2. `quality_candidates`：训练、装备、技能和库存。
3. `fallback_candidates`：征兵及其他低优先级发展动作。

执行顺序：

```text
批量读取 profile/周期/资源/队列的只读快照
  → 判断目标与阻塞状态
  → 生成 priority_candidates
  → 评估资源/队列/策略
  → 有可执行候选则停止生成后续组
  → 只有队列占用、目标完成或明确策略放弃时才生成 quality_candidates
  → 最后才生成 fallback_candidates
```

性能和一致性要求：

- 每个 Profile 每个槽位最多生成当前组；当前实现通过计划内 `candidate_generation_coverage_kinds` 区分尚未生成的后续组，不能把它们统计成资源阻塞；持久化的细粒度 `not_evaluated` 指标仍待后续补齐。
- 候选 builder 只能消费快照、固定 catalog 和 policy release，不得在候选循环中查询数据库或写入状态。
- 每个候选组生成 `candidate_group_digest`。锁内只重读执行所需的最小状态；如果 digest 失效，只重建当前组，不恢复全量候选路径。
- 锁冲突、资源变化和队列变化必须使用有限次数的局部重试；超过上限转为 `lock_retry` 或 `resource_wait`，不得在同一调用内级联生成所有回退组。

### P1-3：队列感知和经济感知评分

在当前 `CandidateAssessment` 的基础上增加：

- 预计完成时间和队列占用时间。
- 当前资源缺口以及自然产出后的可支付时间。
- 未来 24/72 小时工资和招募成本（仅用于同组评分，不作为 V2 普通培养的全局硬门槛）。
- 建筑对银两/粮食产出的边际收益。
- 科技对当前兵种/门客目标的前置价值。
- 动作完成后对周期覆盖目标的贡献。

评分只用于同一优先级组内排序，不能覆盖硬约束。资源恢复阶段同时考虑 `payback_seconds`、目标动作 `next_affordable_at`、队列占用和容量/科技覆盖贡献；不能只按“最短恢复时间”，否则可能长期选择低价值小升级，也不能按最高 utility 让高等级、高成本建筑霸占候选。

资源恢复候选的最小计算应为：

```text
payback_seconds = recovery_cost / max(production_delta_per_second, epsilon)
recovery_value = target_horizon * production_delta - recovery_cost
```

只有 `recovery_value` 达到 policy release 阈值的候选才进入恢复组；其余候选直接记录为 `recovery_not_worthwhile`，避免重复评估。

### P1-4：类型和生命周期画像收口

类型配置继续保留，但需要避免类型目标被全目录随机候选覆盖：

- 均衡型：税务司、农田、银库、建筑学和农耕术保持平衡。
- 肥羊型：优先税务司、银库和高稀有度招募，减少无收益征兵。
- 武馆型：优先铁匠铺、冶炼坊、锻造技和冶炼技，但必须先保证银两生产。
- 护院型：优先家丁房、城防建筑和防御科技，避免资源不足时反复尝试高价防御建筑。
- 弃坑型：低频资源维护、较长动作间隔和较低培养完成度，不创建大量无意义候选。

生命周期 persona 应影响动作间隔、资源目标、门客数量目标、招募频率/卡池权重和培养目标，不应随机伪造正常招募的“完成率”。招募成功与否仍由真实资源、候选池、容量和替换规则决定；培养完成率只能作为观测指标，不能作为绕过领域规则的动作参数。

### P1-5：验证驱动和线上性能分离

15 天回放的慢点来自逐事件、串行、完整 ORM/事务路径，不能直接归因于线上性能。中期应同时优化验证工具和线上读写形态：

- 将回放分为两种模式：`faithful_event` 保留资源结算、领域完成和招募完成的先后顺序，用于业务正确性；`accelerated_projection` 只用于容量/趋势压测，不能作为正确性放行依据。
- 按事件时间排序批量推进，但同一时间点仍按固定优先级处理工资、资源结算、领域完成、招募完成和维护决策，不能因批量化改变业务顺序。
- 对同一批次使用批量快照和固定 catalog，避免每个事件重复读取不变配置；配置、策略和 catalog 在回放期间冻结并带 checksum。
- 将“策略结果验证”和“锁/事务压力验证”拆成两个测试模式；前者允许纯函数快照，后者必须走目标 MySQL/Redis 和真实锁边界。
- 线上维护使用批量 claim、有限批量预加载和最小锁内读取；候选数量增加不能线性增加查询次数。
- 继续使用目标 MySQL/Redis 的 EXPLAIN、并发和长时矩阵验证线上路径，不用本地回放耗时替代性能证据。

## 7. 长期计划：职责拆分与事件驱动（P2）

长期目标是降低 `maintenance.py` 的职责密度，同时保持每个写入边界可追踪。当前文件约 7,800 行，已经出现规划、候选、执行、周期调度、完成对账适配和审计组装混合的迹象，属于中等结构风险，不建议在策略未稳定前立即大搬迁。

### P2-1：按责任拆分维护模块

目标边界：

| 模块 | 责任 | 不负责 |
|---|---|---|
| `maintenance_scheduler` | due 选取、批量预加载、周期唤醒 | 不决定具体动作，不直接写领域对象 |
| `maintenance_phase` | 培养目标、目标缺口和阻塞状态转换 | 不执行资源扣除或领域写入，不管理独立招募替换 |
| `maintenance_candidates` | 构造纯候选和 action spec | 不修改数据库，不推进周期 |
| `maintenance_policy` | 类型、资源、时间和强度硬约束 | 不调用 HTTP、模板或 Celery |
| `maintenance_planner` | 选择优先级组和候选评分 | 不持有长事务，不执行领域动作 |
| `maintenance_executor` | 锁内重验证、事务和领域 command | 不负责 due 扫描和报表 |
| `maintenance_cycle` | 周期槽位、重试、状态和审计 | 不重新实现候选规则 |
| `maintenance_completion` | 建筑/科技/训练完成对账 | 不选择新的培养动作 |
| `maintenance_metrics` | 指标聚合和报表视图 | 不改变业务状态 |

拆分原则：按责任移动逻辑，而不是把现有大函数切成很多只转发参数的薄包装。每次只迁移一个边界，并保留同一组行为测试和 digest 对比。

### P2-2：统一周期状态的单一事实来源

当前纯内存 `MaintenanceCycleState` 与数据库 `BotMaintenanceCycle` 都表达了槽位、覆盖和高价动作等概念，payload 还可能增加目标/阻塞状态。长期目标：

- 数据库周期是运行时唯一事实来源。
- 纯函数只负责验证、计算下一个状态和生成审计 payload，不持有另一份可恢复状态。
- `covered_action_kinds` 从 `action_kind_counts` 派生，避免双写。
- 目标/阻塞状态只保留一份；过渡期 payload 必须有 schema version，迁移完成后再删除重复字段。
- 已不再参与决策的 `high_cost_actions_used` 只在确认无报表、迁移和约束依赖后删除；删除前先完成查询审计和一次性迁移。

### P2-3：完成事件驱动的唤醒闭环

保留周期扫描作为兜底，但长期减少“每分钟扫描所有 due Profile”的依赖：

- 建筑/科技/训练完成、招募完成事件可以直接生成 profile 唤醒信号。
- 资源事件只在 Profile 从“不可支付”变为“可能可支付”，或到达 `next_resource_check_at` 时生成唤醒；不能为每一次自然产出广播所有 Profile。
- 同一 Profile 的唤醒信号通过 `profile_id + wake_reason + due_bucket` 去重，并设置短 TTL 或合并窗口，避免资源结算造成惊群。
- 唤醒消费者仍使用有界批量 claim；同一 Profile 同时只允许一个维护执行者进入锁内路径。
- 扫描任务只处理超时、丢失事件和恢复队列。
- oldest-due、事件延迟、重复唤醒、单 Profile 唤醒频率和丢失恢复进入统一监控。

### P2-4：策略数据化和可回放

将资源影子价格、阶段阈值、类型目标和动作时间成本纳入不可变 policy release：

- policy release 带版本、checksum 和生效时间。
- 已打开周期冻结策略快照，不因热更新改变中途决策。
- 每次候选选择保留最小可解释原因，支持按 Profile 重放一个周期。
- 线上策略变更先跑离线 15/30 天回放，再跑真实 MySQL/Redis 小流量窗口。

## 8. 性能预算与实现门槛

性能优化不能只看一次回放总耗时，必须同时看候选规模、数据库往返、锁竞争、唤醒频率和内存。所有目标先在现有 V2 路径采集 baseline，再以同一批 Profile、同一随机种子和同一 policy release 对比。

### 8.1 线上维护路径

```text
批量 claim due Profile
  → 批量读取只读快照和固定配置
  → 纯函数判断目标/阻塞并生成一个候选组
  → 只对选中 action 做最小锁内复核
  → 提交领域 command 和周期审计
  → 设置下一次槽位/资源/领域唤醒
```

硬约束：

- 候选 builder、selector 和评分函数不得在候选循环内访问 ORM、Redis 或写入状态，避免 N+1 查询和隐藏副作用。
- 锁内不得重新生成全量候选、读取全目录配置或执行无关的统计聚合；只验证选中 action 的资源、队列、目标和幂等凭证。
- 候选数量增加时，查询次数应保持“按 Profile/批次增长”，不能按候选数量线性增长。
- `resource_wait`、`domain_wait` 和 `lock_retry` 只设置下一次唤醒，不在同一任务内忙等或递归调用维护入口。
- 周期 payload 中的历史数组必须有上限；详细审计写入独立事件表或聚合表，不能让单个 Profile 的 payload 无界增长。

### 8.2 性能指标与放行阈值

至少采集以下维度：

| 维度 | 指标 |
|---|---|
| 调度 | 批量大小、claim 数、oldest-due、任务堆积、重复 claim |
| 规划 | 每 Profile/槽位候选生成数、评估数、`not_evaluated` 数、纯函数耗时 |
| 数据库 | 查询数、查询 fingerprint、p50/p95/p99、锁等待、deadlock、事务时长 |
| 唤醒 | 每 Profile 唤醒次数、重复率、事件延迟、资源等待唤醒命中率 |
| 资源 | `next_affordable_at` 误差、资源等待时长、结转比例 |
| 进程 | RSS、swap、OOM、CPU、Redis 队列长度和失败重试 |

建议放行门槛：

- 在相同业务结果下，priority 方案的候选评估数较当前全量路径下降至少 50%，每 Profile/槽位的数据库查询数不随候选数量增长。
- 维护任务 p95 不高于当前 baseline 的 110%；完成索引、快照和 lazy pipeline 后，再以 p95 下降 20% 为优化目标。
- 锁等待、deadlock、任务堆积和重复唤醒不得高于 baseline；任一指标恶化时暂停扩大玩家规模。
- 以 200、500、1000 Profile 批量分别测量，不用 8 名玩家的小样本回放推断线上吞吐。
- 资源持续不足时，每个 Profile 的唤醒频率受退避上限约束，不得按资源自然产出频率线性放大。

上述阈值是工程放行门槛，不是业务策略硬约束；若业务结果改善但性能退化，必须先优化快照/批量/唤醒路径，再扩大回放规模。

### 8.3 回放和线上压测分离

- `faithful_event`：保留领域完成、资源结算、工资、招募和维护决策的因果顺序，用于正确性和分布验收。
- `accelerated_projection`：使用时间桶和批量快照，只用于候选量、资源趋势和容量压测，不能作为领域写入正确性的证据。
- `database_stress`：使用目标 MySQL/Redis、真实事务和锁边界，测量查询计划、并发、锁等待和恢复；不能用纯内存回放代替。
- 三种模式都冻结 policy release、catalog 和随机种子，并输出同一套 `action_kind/stage/reason` 指标，便于结果对齐。

## 9. 边界治理

### 当前成立的边界

- selector、candidate builder 和快照读取路径原则上只读。
- 普通培养、独立招募和竞技场补位有明确触发入口和资源语义。
- 领域写入由对应 service/command 和事务边界拥有。
- 完成对账通过 durable event 反向更新周期，不直接伪造领域完成。
- 运输层只负责触发和结果映射，不应承载培养策略。

### 当前需要关注的边界漂移

- `maintenance.py` 同时承载规划、候选、执行、周期和调度，修改任一策略时容易影响锁内执行。
- 资源拒绝原因和候选回退原因在同一选择器内混合，容易误把资源瓶颈当作普通无候选。
- 周期 payload、内存状态和历史字段存在重复表达，长期会增加恢复和迁移风险。
- 性能验证脚本调用完整业务路径，但没有明确区分业务正确性、数据库压力和回放加速语义。

## 10. 实施顺序与放行门槛

### 阶段 A：策略修正与指标基线

- [ ] 先建立候选生成/评估/提交/完成、查询数、锁等待和唤醒频率 baseline。
- [x] P0-1 资源不足进入有界 `resource_wait`，禁止同一瓶颈资源的无意义回退，并支持目标结转。
- [x] P0-2 引入容量扩张阶段，聚贤庄只由持久化普通门客目标驱动。
- [x] P0-3 最小落地：拆分建筑/科技候选评估次数、成功提交次数和领域完成事件；全候选 generated/submission_attempted 指标仍在 P1 lazy pipeline 中完善。
- [x] P0-4 提供稳定的进度分类器，将 housekeeping、调度等待及各类阻塞从 progress_applied 中剥离；报表接入按后续指标任务推进。
- [x] 已通过单元、事务并发、资源等待上限和 15 天隔离 faithful replay 验证；扩大到 50/200/500/1000 名玩家前仍需补做目标 MySQL/Redis 性能矩阵。

## 11. 验收指标

### 业务正确性

- 每个有建筑/科技目标且资源、队列允许的周期，建筑和科技候选评估覆盖率为 100%；资源或队列阻塞周期必须有对应的 `blocked` 记录和下一次唤醒/结转结果。
- 每周期成功提交数量和候选尝试数量分开统计；不能用“尝试”冒充“完成”。
- 资源不足时不再提交同一瓶颈资源的低优先级消耗动作。
- 容量不足时聚贤庄动作可追踪，容量达标后不再连续升级。
- 独立招募不占普通培养槽位，满员候选尝试不产生虚假失败。
- 重启、重复扫描、锁冲突和完成事件重放不会重复扣资源、重复加等级或重复推进槽位。

### 指标质量

- 实际培养阻塞率与 housekeeping 分开；当前 10.5% 的总 no-action 只能作为历史基线。
- `resource_wait`、`domain_wait`、`lock_retry`、`candidate_exhausted` 均可按 Profile、archetype、动作和周期聚合。
- 每次资源阻塞都记录资源前值、候选成本、预计自然恢复时间和下一次唤醒时间。
- 每周期可以解释为什么没有完成建筑/科技最低动作数。
- `candidate_generated`、`candidate_evaluated`、`submission_attempted`、`submitted` 和 `completed` 可以按 `phase/objective/action_kind/stage/reason` 对账。

### 性能与容量

- 生产批量使用目标 MySQL 的 EXPLAIN 和查询 fingerprint，验证 due 扫描、预加载和锁内重验证的 p50/p95/p99。
- 分别测量批量 200、500、1000 的查询数、写入数、锁等待、deadlock、oldest-due 和队列等待。
- 验证工具回放耗时单独记录，不把串行回放时间当成线上请求延迟。
- 目标主机完成 1 小时、6 小时和 24 小时 RSS、swap、OOM、任务堆积和重启恢复测试。

## 12. 测试要求

每个阶段至少覆盖：

- 纯策略测试：资源不足、队列满、容量不足、目标完成和无候选分支。
- 服务测试：quote、锁内重验证、事务回滚、资源扣除和领域完成事件。
- 并发测试：同一 Profile 重复扫描、资源变化、招募完成与培养同时到达。
- 回放测试：固定随机种子、8/50/200 名玩家、3/15/30 天结果分布。
- 真实服务测试：目标 MySQL/Redis、Celery、锁超时和任务重试。
- 静态检查：`compileall`、YAML 校验、`git diff --check` 以及相关类型/测试门禁。

## 13. 剩余风险

- 当前 15 天结果只有 8 名玩家，不能代表全部 archetype 和人口规模。
- 真实资源生产、工资、招募成本和科技前置仍需使用目标业务库数据校准。
- 竞技场补位的目标驱动流程与普通培养分离，但真实补位窗口仍需单独验收。
- `maintenance.py` 的结构复杂度是中期维护风险，不是当前必须立即迁移的线上故障；在 P0/P1 策略稳定前进行大范围拆分会增加回归面。
- 本路线图不授权直接修改生产数据、切换 routing、删除历史字段或执行 Git 提交；这些动作应在对应实施阶段单独确认和验收。
