# 第二轮请求长尾优化

本轮只处理代码中确认的重复查询、重复写入，并补齐慢请求定位证据。没有修改任务卡扣除规则、次数上限、疗伤计算、玩家数据或数据库结构。

## 改动及实测

1. 帮会科技页复用已加载的科技等级，通过共享纯函数计算容量；原数据库查询接口委托同一公式，业务规则一致。两个容量科技的展示额外 SQL 从 4 次降到 0 次。仅对选中分类生成展示信息，完整分类导航保留。
2. 邮件标记已读仅更新未读记录。真实数据库执行观测确认混合选择已读/未读邮件第一次只更新 1 行，重复请求更新 0 行；所属庄园过滤、未读缓存失效及响应格式保持一致。
3. 请求耗时达到 1000ms 时，现有访问日志追加 `db_execute_count`、`db_execute_ms`、`db_execute_max_ms`。只记录次数和耗时，不记录 SQL 或参数、不发额外查询；快请求日志格式不变。

数据库计时只覆盖请求同步线程的 execute/executemany，包括模板延迟查询和执行失败；包装器会在异常或请求取消后清理。不包含连接建立、事务 commit/rollback、fetch、独立线程或响应返回后的流式查询，不能把剩余耗时直接归因为 Redis 或提交。

## 验证

邮件视图及重复写入、帮会科技视图及服务、访问日志共 93 项交叉回归通过。覆盖三个科技分类、容量边界、未读计数、SQL 失败、取消传播、模板查询、观测开关及快请求格式兼容。七个变更文件 Black 检查通过；日志及新增测试 Ruff 检查通过，四个生产文件语法检查通过。本轮相关文件 diff whitespace 检查通过，仓库其他未发布文件的既有问题没有改动。

补跑 ASGI 与健康检查 29 项通过，本轮共 122 项。没有改动依赖或执行 git 提交。

## 发布方式

四个生产文件修改前 SHA256 与远端镜像逐一一致。以 `webgame:capacity-http-types-20261013` 为基础，仅应用本轮精准补丁构建 `webgame:request-tail-optimization-20261013`，保留已有其余业务代码。使用现有蓝绿流程，候选服务健康后切流并等待旧请求排空；只替换 Web，不触发 migrations 或静态资源生成。

## 效果边界

SQL 数量和重复更新行数的减少已由测试实测；发布后的真实延迟改善仍需积累日志，不能将上线成功等同于所有请求都低于一秒。上轮观察到的数据盘抖动仍需排查，虚拟玩家硬安全暂停保持原状态，本轮没有通过解除保护制造性能结论。

下一次慢请求可先判断最长 SQL 及累计执行耗时是否占据主要时间，再针对具体数据库等待、磁盘或其他阶段继续定位，避免无依据地扩容或重构。
