# 一键疗伤优化复核（2026-10-11）

## Findings

- High，已修复：正常疗伤逐瓶建立保存点、保存门客和扣库存。高血量、低剂量药使数据库操作与瓶数成正比，延长事务及庄园锁占用。最小修复为先按原选药规则计算总治疗量，再每门客治疗一次、每库存扣减一次。
- Medium，已修复：关联模板的锁可能使不同庄园因共用模板互相阻塞。支持 `SELECT FOR UPDATE OF` 的数据库只锁库存和门客自身；真实 MySQL 并发用例验证共用模板的不同庄园可同时治疗。
- 复核未发现新增的高、中等级问题。负生命加成的最大生命值 SQL 计算显式转为有符号整数，避免 MySQL 无符号运算溢出。

## Boundary governance

`guests/services/health.py` 继续拥有事务、锁和治疗提交。规划函数只修改库存副本，不访问数据库或调度训练。提交复用 `heal_guest` 和库存核心，保留绑定库存、忠诚度、重伤解除和训练恢复的业务边界。页面及接口无需修改。

锁序统一为 Manor → InventoryItem → Guest。整轮治疗与扣药在同一事务内；错误的治疗/扣减结果触发断言并回滚，数据库及编程错误不被吞掉。可恢复业务错误先回滚批量保存点，再进入原有逐瓶跳过异常药品的兼容路径。副本隔离内存变更，保存点回滚同时丢弃未提交的训练回调。

## Refactor plan

保留原门客优先级、药品选择、绑定扣减、部分治疗及返回字段。拆分纯规划与事务提交，正常路径消除逐瓶写入；异常路径保留既有容错。过滤满血门客以减少处理和锁范围。没有新增队列、依赖、数据库迁移或前端流程。

## Scope assessment

Surgical Fix：局部性能和并发修复，复用领域服务和库存核心，不进行架构迁移。

## Residual risk

正常路径的数据库写入仍随实际治疗门客和使用库存行数增长；没有用异步任务掩盖事务耗时。药品种类很多时，规划需要重复挑选库存。可恢复业务异常的兼容路径仍可能逐瓶执行，以保留既有错误语义；若线上频繁进入该路径，需要继续定位异常库存原因。没有验证远端整体负载，也不能据此认定所有服务器卡顿都已解决。
