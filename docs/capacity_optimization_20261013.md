## Refactor audit

High 风险是缓存/实时协调与持久任务共用 fsync 链路、无界请求堆积以及提前准入的安全记录；本轮通过角色隔离、HTTP 准入和完整 chunk 收尾处理。Medium 风险是实时生命周期和单轮后台长尾，已补释放、退避、公平续跑及预算。

Boundary governance：HTTP 与协议关闭处理留在 transport 层，claim、资产和安全记录仍由领域 service 及数据库事务拥有；迁移是显式停写的运维命令，读取和指标采集不隐藏业务写入。Refactor plan 为保留业务规则、拆开基础设施用途、缩小准入和批次、增加必要观测。Scope assessment：基础设施为 Structural Shift，业务侧为 Surgical Fix，不是数据模型或游戏架构迁移。Verification 和 Residual risk 见后文测试、实际采样与增长容量边界。

## 已完成的改动

| 层面 | 当前配置及行为 | 解决的问题 |
| --- | --- | --- |
| Web 内存 | 384MB → 768MB | 增加请求与连接的内存余量 |
| 缓存及实时通信 | 独立 `redis_runtime`，数据集 256MB、容器 384MB，noeviction，无 AOF/RDB | 缓存与实时状态不再与任务 broker 的 AOF 落盘共用 Redis 主线程 |
| 任务持久化 | 原 Redis 和原 broker/result 地址保留，AOF 开启，队列未清空 | 保留待执行任务及原持久化语义 |
| HTTP 准入 | 每 Web 进程业务执行 24、等待 48；健康执行 2、等待 2；等待最多 1 秒 | 避免增长或慢依赖导致无限堆积 Django 工作；未准入的请求返回 JSON 503/Retry-After 2，不执行资产逻辑 |
| 实时连接 | 页面退出释放、恢复不重复连接、持续失败退避至 60 秒；关闭后停止推送并回收额度 | 降低不必要连接、重连压力与关闭协议异常 |
| 共享 IP 容量 | 每 IP 20 → 60，每用户仍 12，原握手限速保留 | 减少共享公网 IP 下合法玩家之间争用 |
| 后台培养 | 周期任务 20 秒软预算，完整业务步骤之后暂停 | 不再一轮串行占用过多成员与槽位 |
| 虚拟维护 | 每 10 个成员才准入安全记录，完整收尾后检查 20 秒预算 | 未开始成员不会提前留下安全记录，后续扫描公平续跑 |
| 人口轮换、恢复、单 cell 任务 | 完整创建/恢复及 claim 结算后检查共享 20 秒预算 | 处理 227 秒长尾，避免把余量移到无预算的恢复任务 |
| 运行监控 | systemd 每分钟采样、保存约 14 个完整日及当前日 | 持续记录磁盘延迟、Redis fsync 增量、内存、队列、HTTP P95/5xx、实时拒绝、实例重启 |
| 仅 Web 发布 | 候选健康后切换代理，旧 HTTP 排空，再替换 canonical Web | 本轮 HTTP 补丁已实际采用蓝绿发布，未停止 worker/Redis |

## 迁移与发布安全

首次 Redis 角色切换涉及所有 cache/channel 写方，所以统一进入维护入口，温停生产者、Web 和全部 worker，确认没有运行实例或强杀退出，再复制状态。

DB1 的 41 个 zset、DB2 的 8617 个键（8613 string、1 set、3 zset）经过二进制内容、类型与绝对过期时间校验；两个源/目标审计一致。工具不修改源，不复制 broker DB0，不延长锁或消息寿命，不覆盖非空目标。所有服务统一切换后通过 readiness，再恢复公网入口。

维护入口从北京时间 18:05:34 至约 18:06:27，共约 53 秒。期间明确返回维护 503，而非把玩家请求发送到未启动的后端。静态资源预先生成，保留旧 hash，新版重连脚本的公开资源内容已验证。

随后 HTTP 小补丁通过蓝绿工具发布：健康候选承接流量，等待旧 HTTP 65 秒，更新正式 Web，再切回并等待候选 HTTP 排空。候选仅按本次随机名称和 owner label 清理，后台服务不重建。工具不会在失败时切向不健康实例。

## 增长容量与验收边界

4 核、约 8GB 的当前主机先采用有界工作量，而不是增加所有线程、进程和数据库连接。HTTP 容量为每进程，不能把 24 个并发请求等同于 24 个玩家。

隔离的 100 请求突发用例验证：最多 24 个业务同时执行，48 个请求等待，28 个请求在执行前得到 503；健康请求在全部业务名额被占用时仍可完成。它证明准入边界、不是线上吞吐量或支持玩家数的承诺。

后台测试验证完整 claim/动作/finalize、安全记录终结、预算暂停、下轮恢复、等待更久成员及地区公平性。软预算不是硬截止：单个不可分割步骤或一个已准入 chunk 可以超过 20 秒，但不会为了计时强杀事务。

新增与相关验证包括真实双 Redis 迁移、Compose 合并、监控、HTTP/ASGI、100 请求突发、蓝绿状态机、后台主套和人口最后补丁；相关测试均通过，Black/flake8/isort/目标类型与语法检查通过。最后补齐 ASGI 请求与响应的标准类型声明，并明确默认 `trailers=False`、`more_body=False`；两个文件 mypy 及 23 项 HTTP/ASGI/突发回归通过，再通过蓝绿同步到最终镜像。此前实时/前端/培养回归也通过。仓库架构检查另有 1 项既有失败：未上线的 `guests/admin.py` 新读取关系未登记白名单，该文件不在本次发布范围，未通过更改白名单掩盖问题。

## 上线后的实际采样

- 最终 Web 约 147MiB / 768MiB，主机可用内存约 3988MB。
- 六个任务队列快照均为 0。
- runtime Redis 无 AOF、noeviction，原任务 Redis AOF 保留；无驱逐或拒绝连接。
- 所有 readiness 项通过；首页、登录页、存活检查返回 200，最后三次对应约 73ms、76ms、68ms。
- 最后五分钟 Web 日志没有 traceback、Redis 读取超时、关闭协议或 Internal Server Error 记录。
- 磁盘采样区间平均 I/O 等待约 0.18ms、busy 约 3%，这不是事故时的磁盘数据。
- 监控没有采集错误；MySQL 内存超过容器 85% 的黄色提示仍存在，应结合工作集、文件缓存、连接和增长曲线观察。

Web 和 worker 刚重建，较低内存含重建释放旧堆的影响，不能据此宣称内存泄漏已消除。早期无超时也不能代替后续高峰和 fsync 事件的趋势。

## 后续扩容判据

先查看 `/data/webgame-monitor/metrics-YYYY-MM-DD.jsonl` 和 timer 的 journal。监控限制 CPU 为单核 20%、内存 256MB、单次日志读取 64MB；不在 Web 内启动 Django 诊断进程，不存 cookie、请求头、IP、查询参数或玩家资产内容。

| 持续出现的指标 | 优先动作 |
| --- | --- |
| Web 工作内存接近 85% 或 HTTP P95 持续超过 500ms | 先看并发、SQL/模板及内存趋势；评估第二个 Web 实例，不先放大等待队列 |
| host MemAvailable 接近 1GB | 不再追加 worker/缓存限额；评估迁出其他负载或升级主机 |
| runtime 数据集超过 80% | 检查 TTL、热键和增长来源；在总内存预算内扩 runtime 或规划独立缓存主机 |
| 持续队列积压且完成速度不足 | 判断是 CPU、数据库还是业务步骤慢，再增加对应队列消费者；保留幂等、锁和每批预算 |
| 数据盘平均 I/O 延迟高、broker fsync 计数持续增加 | 对齐磁盘/SQL/任务时间，检查云盘性能与写入量；缓存隔离不能解决 MySQL/持久 broker 的物理盘延迟 |
| 大量合法共享 IP 用户仍触及连接限额 | 评估跨标签页共享连接、连接复用与缓存 fan-out；保留会话/Origin和限速保护 |

在单请求单数据库连接的保守预算下，两个 Web 的业务执行上限约 48，再加健康通道和后台消费者仍应保留 MySQL 96 连接上限的余量；这只是规划估算，需实测连接峰值与 HTTP 负载后才部署第二实例。本轮没有声称已经配置多副本负载均衡或支持某个固定在线人数。

runtime Redis 重启会失去其易变数据；计划重启必须停写，意外重启应视为协调状态丢失事件，检查在途任务并恢复，不能只看 PING 成功。监控记录重启及数据集压力，但不会自动清空缓存或重启游戏服务。MySQL 与持久 broker 仍共用数据盘，云盘/宿主机抖动仍需凭新增历史指标定位。
