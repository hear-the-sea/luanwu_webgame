# 春秋乱世庄园主后端面试问答手册

> 适用场景：把本项目作为后端求职项目写进简历，并准备面试官围绕项目做技术追问。
>
> 项目定位：基于 Django 5 的多人在线策略经营游戏后端，重点不是普通 CRUD，而是复杂玩法状态机、事务一致性、异步任务、实时通信、Redis 降级、数据驱动配置和测试门禁。

## 1. 面试时怎么介绍这个项目

### 1.1 一句话介绍

这是一个基于 `Django 5 + MySQL + Redis + Celery + Channels` 的多人在线策略经营游戏后端，包含庄园经营、门客培养、战斗、交易行、拍卖、帮会、地图、消息通知和世界聊天等模块。

### 1.2 30 秒版本

我做的是一个 Django 多人在线策略经营游戏项目。后端主要使用 Django 5，数据库使用 MySQL，Redis 用于缓存、Celery broker、Channels channel layer 和聊天历史。项目里比较核心的难点不是页面 CRUD，而是游戏状态机和并发一致性，比如门客不能同时出征两场战斗、拍卖不能被重复结算、库存不能被并发扣成负数。为了解决这些问题，项目使用 `transaction.atomic()`、`select_for_update()`、Celery 多队列、周期扫描兜底、WebSocket 实时通信，以及真实 MySQL/Redis 集成测试。

### 1.3 2 分钟版本

这个项目是一个以春秋战国为背景的多人在线策略经营游戏。架构上采用 Django Template 作为页面层，后端按领域拆成 `accounts`、`gameplay`、`guests`、`battle`、`trade`、`guilds`、`websocket` 等 app。

其中 `gameplay` 负责庄园、建筑、任务、地图、竞技场等核心玩法；`guests` 负责门客招募、培养、装备和技能；`battle` 负责战斗模拟和战报；`trade` 负责商铺、银庄、交易行、拍卖；`guilds` 负责帮会、科技、仓库和英雄池；`websocket` 负责通知、在线人数和世界聊天。

技术上，HTTP 页面和 WebSocket 共享同一套业务服务层。异步任务使用 Celery，拆分了 `default`、`battle`、`timer` 队列，分别处理普通任务、战斗任务和定时状态推进任务。Redis 同时承担 Django cache、Celery broker/result、Channels channel layer、限流和聊天历史等职责。

这个项目最有价值的地方是后端工程复杂度比较真实：很多玩法都有状态推进和并发风险。比如拍卖结算可能被多个 worker 同时触发，门客可能被多个请求同时出征，交易库存可能被并发扣减。项目通过数据库事务、行锁、状态检查、唯一约束和真实服务集成测试来保证一致性。

## 3. 技术栈问答

### Q1：这个项目用了什么技术栈？

推荐回答：

项目后端主要是 Python 3.12 和 Django 5。数据库方面，本地默认可以用 SQLite，真实服务环境使用 MySQL 8.x。Redis 用于缓存、Celery broker/result backend、Channels channel layer、聊天历史和限流。异步任务使用 Celery 和 Celery beat。实时通信使用 Django Channels 和 Daphne。接口文档能力使用 DRF 和 drf-spectacular，不过项目不是纯 REST API 平台，主要入口还是 Django Template 页面和表单 POST。前端是 Django Templates、Tailwind CSS 和手写 JavaScript。

技术细节：

- `Django`：处理 HTTP 请求、模板渲染、ORM、认证、Session、Admin。
- `MySQL`：真实环境数据库，验证事务、行锁、唯一约束和并发语义。
- `Redis`：缓存、消息广播、Celery broker、聊天历史、限流。
- `Celery`：异步任务和周期任务。
- `Channels`：WebSocket，支持通知、在线人数、世界聊天。
- `Daphne`：ASGI server，同时承载 HTTP 和 WebSocket。
- `Tailwind CSS`：构建样式。
- `pytest`：单元测试和集成测试。

面试官可能追问：为什么项目装了 DRF，但又说不是 REST API 平台？

回答：

因为这个项目主要交互方式是 Django Template 页面、表单 POST 和少量 JSON 接口。DRF 和 drf-spectacular 主要用于接口文档和局部 API 能力，不是把全部业务都设计成 RESTful API。这个选择符合项目阶段：优先快速实现复杂玩法，而不是先构建完整前后端分离架构。

避坑点：

不要说“前端用了 Vue/React”，这个项目当前不是 SPA，也没有 JS bundler。

## 4. 架构与模块划分问答

### Q2：你怎么划分项目模块？

推荐回答：

项目按业务领域拆分 Django app：

- `accounts`：用户、登录、单会话控制。
- `gameplay`：庄园、建筑、资源、任务、地图、竞技场、生产等主玩法。
- `guests`：门客模板、招募、培养、装备、技能、工资和叛逃。
- `battle`：战斗模拟、战斗报告、奖励发放。
- `trade`：商铺、银庄、交易行、拍卖。
- `guilds`：帮会、成员、科技、仓库、英雄池、帮会任务。
- `websocket`：通知、在线统计、世界聊天。
- `core`：健康检查、中间件、基础设施工具。

技术细节：

这种拆分方式不是按技术层，比如全部 models 放一起、全部 services 放一起，而是按业务边界拆。好处是每个 app 更接近一个业务域，方便维护和测试。

面试官可能追问：`gameplay` 会不会太大？

回答：

会有这个风险。`gameplay` 现在是主玩法聚合层，包含庄园、地图、任务、生产、竞技场等多个子领域。项目已经通过 `gameplay/models/`、`gameplay/services/`、`gameplay/views/` 下面的子模块拆分来缓解。后续如果某些子领域继续变大，比如竞技场或地图 PVP，可以再拆成独立 app。

### Q3：View / Service / Model 怎么分工？

推荐回答：

View 负责请求层，主要做参数解析、权限校验、表单处理和响应组织。Service 负责业务逻辑、事务边界、状态推进和跨模块协调。Model 负责数据库字段、关系、索引、约束和基础数据结构。

比如拍卖出价，View 不应该直接扣金条、改竞价记录、写冻结记录，而应该调用 Service。Service 在事务里完成锁定、校验、扣减或冻结、写记录。这样业务规则集中在 Service，方便测试，也避免多个入口重复实现。

技术细节：

典型后端项目里最容易出问题的是把复杂业务写在 View 里。这样会导致：

- 事务边界不清楚。
- 代码难测试。
- 多个页面入口容易复制逻辑。
- 异常补偿和日志分散。

项目里像拍卖、战斗、门客招募、帮会仓库等都更适合放 Service。

面试官可能追问：Service 层是不是 Django 官方推荐？

回答：

Django 官方没有强制 Service 层模式，但对于复杂业务系统，Service 层是一种常见工程组织方式。简单 CRUD 可以直接在 View 或 Model 里处理，但这个项目涉及跨表事务、状态机和异步任务，所以 Service 层能让业务边界更清晰。

## 5. 为什么不是前后端分离

### Q4：为什么用 Django Template，而不是 React/Vue SPA？

推荐回答：

这个项目早期最大的复杂度在后端玩法状态机，而不是前端组件体系。Django Template 能直接复用 Django 的 Session、权限、CSRF、Messages、表单和上下文，开发效率更高。对于经营类游戏后台页面，很多页面是服务端渲染加少量交互，没必要一开始就引入完整 SPA。

技术取舍：

优点：

- 开发链路短，后端渲染页面快。
- 认证、权限、CSRF、Session 集成简单。
- 不需要维护复杂的前端路由和状态管理。
- 适合表单 POST 和后台式页面。

缺点：

- 复杂交互会让手写 JS 分散。
- 页面局部状态管理不如前端框架清晰。
- 如果后续实时交互很多，可能需要局部组件化或迁移到前后端分离。

面试官可能追问：什么时候你会考虑改成 SPA？

回答：

如果游戏交互变成大量局部刷新、拖拽编队、实时战斗表现、复杂地图操作和跨页面前端状态共享，我会考虑引入 Vue/React，或者先在局部高交互页面做组件化，而不是一次性全量重写。

## 6. 并发与事务问答

### Q5：这个项目有哪些并发问题？

推荐回答：

主要有四类：

1. 同一个门客可能被多个请求同时出征、训练或打工。
2. 同一个拍卖轮次可能被多个 worker 同时结算。
3. 同一个库存可能被多个请求同时扣减。
4. 定时任务和用户请求可能同时推进同一条状态记录。

这些问题如果只靠普通查询和更新，很容易出现重复扣减、重复发奖、状态错乱。

技术细节：

比如门客出征：

```text
请求 A 查询门客状态：IDLE
请求 B 查询门客状态：IDLE
请求 A 设置为 DEPLOYED
请求 B 也设置为 DEPLOYED
```

如果没有锁，两个请求都认为自己成功了。正确方式是在事务里锁定门客行，重新检查状态，再推进状态。

### Q6：`transaction.atomic()` 是什么？为什么要用？

推荐回答：

`transaction.atomic()` 是 Django 提供的事务上下文。放在里面的数据库操作要么全部成功提交，要么发生异常时全部回滚。

在这个项目里，一个业务动作通常不是单表更新。例如拍卖出价可能要检查庄园资产、冻结金条、写出价记录、更新拍卖位价格。如果中间失败，不能只完成一半，所以需要事务。

技术细节：

事务适合包住必须保持一致的一组数据库操作。但事务不能太长，尤其不要在事务里做耗时计算、网络请求或 WebSocket 广播，因为事务越长，锁持有时间越长，越容易阻塞和死锁。

面试官可能追问：事务里可以发通知吗？

回答：

不建议直接发。通知、缓存刷新、WebSocket 广播属于外部副作用。更稳妥的是数据库事务提交后通过 `transaction.on_commit()` 再发，避免事务回滚了但通知已经发出。

### Q7：`select_for_update()` 是什么？解决什么问题？

推荐回答：

`select_for_update()` 是数据库行级锁。它会在事务中锁定查询到的行，直到事务提交或回滚。其他事务如果也想锁这些行，就需要等待。

它解决的是并发写同一条或同一组业务记录的问题，比如：

- 锁门客，防止同一个门客同时出征。
- 锁庄园和库存，防止资源被并发扣减。
- 锁拍卖轮次或拍卖位，防止重复结算。

技术细节：

必须注意：

- `select_for_update()` 必须放在 `transaction.atomic()` 里。
- 锁住后要重新检查状态。
- 多行锁定时要固定顺序，例如按 id 排序，减少死锁。
- SQLite 对行锁支持和 MySQL 不同，不能用 SQLite 测试证明真实并发安全。

面试官可能追问：为什么只判断状态不够？

回答：

因为存在竞态条件。两个请求可能同时读到同一个旧状态。只有在事务内锁定行，再检查状态，再更新，才能保证同一时间只有一个事务推进成功。

### Q8：如何减少死锁？

推荐回答：

死锁无法百分百避免，但可以降低概率：

1. 固定加锁顺序，比如先锁庄园，再锁门客，再锁库存。
2. 多行锁定时按主键排序。
3. 事务尽量短，只在事务内做必要的检查和写入。
4. 不在事务里做耗时计算、外部网络请求或复杂循环。
5. 对可重试的数据库异常设计重试或返回“请稍后再试”。

举例：

如果请求 A 先锁门客再锁庄园，请求 B 先锁庄园再锁门客，就可能互相等待。统一顺序后，死锁概率会下降。

### Q9：悲观锁和乐观锁怎么选？

推荐回答：

悲观锁适合冲突成本高的场景，比如资产扣减、拍卖结算、门客出征。它的思路是先锁住，确保别人不能同时改。

乐观锁适合冲突概率低的场景，比如用版本号或条件更新：

```text
UPDATE table SET status='done'
WHERE id=1 AND status='pending'
```

如果影响行数是 0，说明状态已经被别人改了。

本项目里高风险状态机更偏向悲观锁，因为重复发奖、库存为负、门客状态错乱的成本比较高。

### Q10：`select_for_update(skip_locked=True)` 可以用吗？

推荐回答：

可以，但要看场景。`skip_locked=True` 适合后台批处理扫描，比如多个 worker 扫描待完成任务，可以跳过正在被其他事务处理的记录，提高吞吐。

但它不适合用户强交互请求。比如用户点击领取奖励，如果记录被锁了，直接跳过可能会让用户误以为没有奖励。用户请求更适合等待、重试或提示稍后再试。

## 7. 拍卖系统问答

### Q11：拍卖系统的核心难点是什么？

推荐回答：

拍卖系统的核心难点是资产一致性和重复结算问题。用户出价时要冻结金条，结算时要确认赢家、扣除实际成交价、退还失败者冻结资产、发放物品和通知用户。如果多个 worker 同时结算同一轮拍卖，就可能重复扣款或重复发奖。

技术细节：

拍卖结算需要做到：

- 结算前锁定拍卖轮次或拍卖位。
- 在事务内检查状态是否仍然可结算。
- 结算完成后把状态改为已完成。
- 失败者退款。
- 赢家扣款和发奖。
- 通知失败不能影响核心资产一致性，必要时有 fallback 发放。

### Q12：如何防止拍卖重复结算？

推荐回答：

通过“事务 + 行锁 + 状态检查”。结算开始时锁定拍卖轮次或拍卖位，只有状态还是 `ACTIVE` 或待结算时才继续。第一个事务提交后会把状态改成 `COMPLETED`。第二个并发事务拿到锁后重新读取状态，发现已经完成，就跳过。

初学者理解：

不要理解成“我判断了一次状态就安全了”。关键是：

```text
锁住记录 -> 在锁内重新判断状态 -> 更新状态 -> 提交事务
```

面试官可能追问：如果消息通知失败怎么办？

回答：

通知失败不应该导致核心结算回滚。拍卖的核心一致性是资产和物品。通知属于附加副作用，可以记录日志、降级，或者直接给物品发放 fallback，后续再补通知。

### Q13：维克里拍卖是什么？项目里怎么体现？

推荐回答：

维克里拍卖通常指第二价格拍卖，即最高出价者获胜，但支付价格不是自己的最高出价，而是按第二高价格或规则计算的结算价。项目中拍卖结算会根据 slot 排名计算赢家和结算价格。如果赢家出价高于结算价，多冻结的金条需要退还。

技术细节：

这种机制要求冻结资产和最终扣款分开：

- 出价时按出价金额冻结。
- 结算时只消耗成交价。
- 多冻结的部分退还。

面试官可能追问：为什么不直接出价时扣掉？

回答：

因为出价者可能不是赢家，或者最终结算价低于出价。直接扣掉会增加退款和用户资产解释成本。冻结能表达“这部分资产暂时不可用，但还不一定真正消费”。

## 8. 战斗与门客状态问答

### Q14：战斗系统怎么设计？

推荐回答：

战斗系统大致分为战斗准备、参与者构建、战斗模拟、战报生成、奖励发放和状态释放。门客、兵种、科技、装备和技能会影响战斗属性。战斗入口会构建攻击方和防守方单位，使用随机种子生成可复现的模拟过程，最后生成战报和奖励。

技术细节：

战斗不是简单地“扣血得结果”，它涉及：

- 攻击方门客。
- 防守方门客或 AI。
- 兵种配置。
- 科技加成。
- 装备加成。
- 技能效果。
- 随机种子。
- 掉落表。
- 战报记录。

### Q15：门客为什么需要状态锁？

推荐回答：

因为门客是有限资源，同一个门客不能同时训练、打工、出征或参加多场战斗。如果没有状态锁，多个请求可能同时把同一个门客拿去执行不同玩法。

项目里的做法是：

1. 收集门客 id。
2. 在事务中按顺序锁定门客行。
3. 检查门客状态是否允许出战。
4. 把状态改为 `DEPLOYED`。
5. 战斗完成后释放回空闲或其他状态。

面试官可能追问：如果战斗过程中异常，门客会不会一直卡住？

回答：

需要 finally 释放状态，并且最好提供孤儿状态恢复逻辑。项目里就有处理异常后门客卡在 `DEPLOYED` 的恢复思路，避免用户资产永久不可用。

### Q16：战斗如何保证可复现？

推荐回答：

可复现主要依赖随机种子和输入快照。战斗开始时确定 seed，战斗过程使用受控随机源。战报里保存关键输入和结果，例如参与单位、兵种、技能、伤害过程、掉落等。这样后续可以根据 seed 和输入复盘。

面试官可能追问：为什么不能直接用全局 `random`？

回答：

全局随机源不可控，其他代码也可能消耗随机数，导致结果难复现。战斗这类需要审计和复盘的逻辑最好用独立 `random.Random(seed)`。

## 9. Celery 异步任务问答

### Q17：项目为什么使用 Celery？

推荐回答：

因为项目里有很多不适合在 HTTP 请求中同步完成的任务：

- 战斗报告生成可能比较重。
- 建筑升级、任务完成、招募训练需要到时间后推进状态。
- 拍卖结算、交易行过期处理需要后台定时扫描。
- 帮会生产、日志清理、每日忠诚度处理等适合后台任务。

Celery 可以把这些任务从用户请求中拆出去，提升响应速度，也方便定时调度。

### Q18：为什么拆 `default`、`battle`、`timer` 队列？

推荐回答：

因为任务类型不同，资源需求和时效要求也不同。

- `default`：普通后台任务。
- `battle`：战斗相关任务，可能计算量较大。
- `timer`：定时扫描和状态推进任务，例如任务完成、拍卖结算。

如果所有任务都放一个队列，战斗重任务可能阻塞定时扫描，导致建筑升级、任务完成、拍卖结算延迟。拆队列后可以独立配置 worker 数量和并发。

面试官可能追问：为什么 Celery worker 设置 `prefetch-multiplier=1`？

回答：

为了避免 worker 一次预取太多任务。对于耗时不均的任务，如果某个 worker 抢了很多长任务，其他 worker 空闲也帮不上忙，会影响公平性和延迟。`prefetch-multiplier=1` 更适合需要及时推进状态的任务队列。

### Q19：Celery 任务如何保证幂等？

推荐回答：

幂等就是同一个任务执行一次和执行多次，最终结果应该一致或至少不会重复产生副作用。

项目里状态推进类任务不能只相信任务参数，而是执行时重新查数据库，在事务里锁定记录，检查状态是否仍然待处理。如果状态已经完成，任务直接跳过。

举例：

```text
complete_mission(run_id)
1. 查 MissionRun
2. 锁定这条记录
3. 判断状态是不是 running 且已到完成时间
4. 如果是，发奖励并改成 completed
5. 如果不是，跳过
```

面试官可能追问：任务执行一半失败怎么办？

回答：

数据库操作应该在事务中，失败就回滚。事务外副作用要么放到 `on_commit()` 后执行，要么设计补偿和重试。例如通知失败不应该导致资产状态混乱。

### Q20：为什么需要周期扫描，而不是只用 ETA/countdown 任务？

推荐回答：

ETA 任务更精确，但依赖 broker 和 worker 稳定。如果 worker 重启、broker 抖动、部署中断，任务可能延迟甚至丢失。周期扫描虽然有延迟，但恢复能力更强。对于游戏业务，到期状态晚几十秒或几分钟通常可以接受，但不能永远不完成。

所以项目采用扫描兜底：即使单次任务失败，扫描任务也会把到期记录推进掉。

面试官可能追问：扫描会不会重复处理？

回答：

会有并发可能，所以扫描处理时仍然要事务、行锁和状态检查。扫描任务本身不能假设只有自己在处理。

## 10. Redis 问答

### Q21：Redis 在项目里做了什么？

推荐回答：

Redis 在项目里有多个角色：

- Django cache。
- Celery broker 和 result backend。
- Channels channel layer。
- WebSocket 世界聊天历史。
- 在线人数统计缓存。
- 限流。
- 一些短期 best-effort lock。

技术细节：

Redis 很快，适合短期、高频、可过期的数据。但 Redis 不应该替代数据库作为强一致资产账本。比如库存和金条最终仍然以 MySQL 数据为准。

### Q22：Redis 故障时怎么办？

推荐回答：

要区分功能类型：

- 强一致路径，比如资产扣减、状态推进、锁失败，应该倾向 fail closed，也就是拒绝操作或提示稍后再试。
- 展示类功能，比如在线人数、聊天历史，可以降级，返回空数据或提示暂不可用。
- 异步和实时能力，比如 Celery 和 Channels，Redis 故障会影响比较大，需要健康检查和运维恢复。

面试官可能追问：为什么不能都 fallback 到本地内存？

回答：

本地内存只在单进程内有效，多 worker、多容器之间不共享。它可以用于低风险展示降级，但不能用于分布式锁、资产扣减或跨进程广播。

### Q23：Redis 锁有什么坑？

推荐回答：

Redis 锁至少要注意：

1. 必须设置 TTL，防止进程崩溃后锁永远不释放。
2. 锁值要有随机 token，释放时只释放自己持有的锁。
3. 释放时最好用 Lua 脚本做 compare-and-delete，避免误删别人的锁。
4. 单 Redis 锁不是严格数据库事务锁，高风险资产一致性仍然要依赖数据库事务和行锁。

初学者理解：

错误做法：

```text
DEL lock_key
```

这样可能删掉别人刚拿到的锁。

正确思路：

```text
如果 lock_key 当前值等于我的 token，才删除
```

### Q24：Cache Aside 是什么？项目里如何避免脏缓存？

推荐回答：

Cache Aside 是常见缓存模式：读数据时先读缓存，缓存没有再查数据库并写入缓存；写数据时先写数据库，再删除或刷新缓存。

避免脏缓存的关键是：数据库事务提交后再删除缓存。否则事务还没提交，别的请求可能读到旧数据并重新写回缓存。

面试官可能追问：缓存一致性可以百分百保证吗？

回答：

很难百分百保证。通常通过短 TTL、事务后失效、关键数据不依赖缓存、必要时主动刷新来降低风险。对游戏资产这类强一致数据，不能只相信缓存。

## 11. WebSocket 问答

### Q25：项目的 WebSocket 用来做什么？

推荐回答：

主要有三类：

- 用户通知：比如拍卖结果、消息提醒。
- 在线人数统计：广播当前在线用户数量。
- 世界聊天：实时发送聊天消息。

项目使用 Django Channels，ASGI server 是 Daphne，跨进程广播依赖 Redis channel layer。

### Q26：WebSocket 如何鉴权？

推荐回答：

Channels 使用 `AuthMiddlewareStack` 复用 Django Session。连接建立时可以从 `scope["user"]` 获取当前用户。如果用户未登录，就拒绝连接。项目还做了单会话校验，防止用户在其他地方登录后旧 WebSocket 连接继续操作。

面试官可能追问：为什么接收消息时还要再次校验 session？

回答：

因为 WebSocket 是长连接。用户连接成功后，HTTP session 可能在另一个设备登录时失效。如果只在 connect 时校验，旧连接可能继续发消息。所以接收关键消息时也要检查当前 session 是否仍然有效。

### Q27：channel layer 的作用是什么？

推荐回答：

channel layer 用于跨进程消息广播。WebSocket 连接可能分散在不同 worker 进程或不同容器里。一个用户在 A worker，另一个用户在 B worker，如果没有 Redis channel layer，A worker 无法直接把消息广播给 B worker 上的连接。

初学者理解：

Redis channel layer 就像一个中转站：

```text
worker A 发送 group 消息 -> Redis -> worker B/C/D 收到并推给各自连接
```

### Q28：世界聊天发送流程是什么？

推荐回答：

世界聊天大致流程：

1. 检查用户是否登录。
2. 检查单会话是否有效。
3. 校验消息类型和文本。
4. 文本规范化和长度限制。
5. 频率限制，防刷屏。
6. 消耗小喇叭道具。
7. 写入 Redis 聊天历史。
8. 通过 channel layer 广播给世界频道。
9. 如果失败，尝试补偿并返还道具。

面试官可能追问：为什么要先扣道具再广播？

回答：

因为发送世界聊天是一个消耗道具的动作，扣道具是业务前置条件。但扣道具后广播可能失败，所以必须有补偿机制。如果广播失败，要尝试移除历史并返还道具。

### Q29：聊天历史为什么用 Redis List？

推荐回答：

世界聊天只需要保存最近 N 条消息和短期历史，不需要复杂关系查询。Redis List 的 `LPUSH`、`LRANGE`、`LTRIM` 很适合这种场景。再配合 TTL 控制生命周期，比每条消息都落 MySQL 更轻。

面试官可能追问：Lua 脚本有什么作用？

回答：

Lua 脚本可以把多步 Redis 操作放到 Redis 服务端原子执行，减少网络往返。项目里用于裁剪过期聊天历史。如果 Lua 不可用，也有 Python fallback。

## 12. 数据库设计问答

### Q30：项目数据库设计的重点是什么？

推荐回答：

重点是状态机建模、索引和约束。游戏里很多模型都有状态字段，比如任务运行中/完成、拍卖活跃/已完成、门客空闲/出征/训练、交易挂单活跃/售出/过期。后台扫描和用户查询都依赖这些状态字段。

技术细节：

常见设计包括：

- 状态字段：表达业务生命周期。
- 时间字段：表达开始时间、完成时间、过期时间。
- 复合索引：支持 `status + complete_at` 这类扫描。
- 唯一约束：保护业务不变量。
- 外键关系：保证模板、用户、庄园等关系正确。

### Q31：为什么要加复合索引？

推荐回答：

因为真实查询通常不只按一个字段查。比如扫描到期任务：

```text
WHERE status = 'running' AND complete_at <= now
```

如果只给 `status` 或 `complete_at` 单独建索引，效果可能不如复合索引。复合索引要根据查询条件和排序方式设计。

面试官可能追问：索引越多越好吗？

回答：

不是。索引会占空间，也会降低写入速度。只有能对应真实查询路径、排序路径、后台扫描路径或约束需求的索引才值得加。

### Q32：条件唯一约束有什么用？

推荐回答：

条件唯一约束可以表达“只在某些条件下唯一”。比如同一个用户只能有一个活跃会话，同一主体只能有一个活跃任务。这比只靠业务代码判断更可靠，因为数据库是最后防线。

初学者理解：

业务代码判断可能被并发绕过，但数据库唯一约束不会轻易被绕过。即使两个请求同时插入，数据库也会拒绝其中一个。

### Q33：事务里能不能做很重的计算？

推荐回答：

尽量不要。事务越长，锁持有时间越长，其他请求等待越久，死锁概率也更高。正确做法是：

- 事务外准备输入和计算可提前计算的内容。
- 事务内只做锁定、状态检查、关键写入。
- 事务提交后再做通知、广播、缓存失效等副作用。

## 13. YAML 数据驱动问答

### Q34：为什么使用 YAML 配置玩法？

推荐回答：

游戏数值变化频繁，例如建筑产出、任务奖励、门客成长、拍卖物品、商铺商品、竞技场奖励等。如果每次调整都改代码，成本高且容易出错。YAML 可以把数值配置和代码逻辑分开，方便迭代。

技术细节：

项目里的 YAML 大致分两类：

1. 运行期规则：服务直接读取并缓存，比如商铺、拍卖、竞技场、帮会规则。
2. 模板主数据：通过 management command 导入数据库，比如建筑模板、物品模板、门客模板、任务模板。

### Q35：YAML 配置怎么保证不出错？

推荐回答：

需要 schema 校验和加载器校验。项目提供 `validate_yaml_configs` 命令，检查字段类型、必填字段、覆盖范围等。上线前应该把 YAML 和代码视为同一个版本单元，一起校验和发布。

面试官可能追问：为什么不能完全相信策划填的 YAML？

回答：

配置也是代码的一部分。字段拼错、类型错误、key 改名、引用不存在都会导致线上报错。所以必须有校验、默认值策略和发布流程。

### Q36：配置热更新有什么风险？

推荐回答：

多进程环境下，每个进程都有自己的内存缓存。一个进程刷新不代表所有 Web worker 和 Celery worker 都刷新了。对于支持热更新的配置，可以通过统一命令清缓存并重新加载；对于没有纳入热更新的配置，需要重启相关进程。

面试官可能追问：如果旧数据引用了被删除的配置 key 怎么办？

回答：

不能直接删。需要先检查数据库引用，必要时做兼容映射、迁移脚本或数据回填。配置 key 应该像数据库主键一样谨慎维护。

## 14. 测试体系问答

### Q37：项目测试怎么分层？

推荐回答：

项目有两层测试门禁：

1. Hermetic 快速测试：使用 SQLite、LocMem cache、InMemory channel layer、memory Celery，反馈快，适合日常开发。
2. Real external-service 测试：使用真实 MySQL 和 Redis，验证行锁、事务、Redis、Channels、Celery 等真实语义。

这两层目的不同，不能互相替代。

### Q38：为什么 SQLite 测试不能证明并发安全？

推荐回答：

SQLite 的锁机制和 MySQL 不同，`select_for_update()` 在 SQLite 下不能代表真实 MySQL 行级锁行为。并发状态机，比如拍卖结算、库存扣减、门客出征，必须用真实 MySQL 验证。

面试官可能追问：那 SQLite 测试还有价值吗？

回答：

有。SQLite 测试启动快，适合验证纯业务逻辑、配置解析、普通 Service 行为、页面基础行为。但它不适合验证真实并发和 Redis 语义。

### Q39：怎么写并发测试？

推荐回答：

通常使用 `pytest.mark.django_db(transaction=True)`，让测试真正使用事务和多个数据库连接。然后用多个线程同时触发同一个写路径，最后断言最终状态：

- 只结算一次。
- 库存没有扣成负数。
- 奖励没有重复发。
- 状态最终正确。

面试官可能追问：为什么要 `transaction=True`？

回答：

普通 Django 测试可能把测试包在外层事务里，不适合验证多个连接之间的真实提交和锁等待。并发测试需要更接近真实数据库事务行为，所以要 `transaction=True`。

### Q40：单元测试和集成测试怎么区分？

推荐回答：

纯函数、规则计算、配置解析、Service 内部小逻辑适合单元测试。数据库事务、行锁、Redis、Channels、Celery、WebSocket 这类依赖真实基础设施的能力适合集成测试。

## 15. 健康检查与可观测性问答

### Q41：`/health/live` 和 `/health/ready` 有什么区别？

推荐回答：

`live` 只表示进程还活着。`ready` 表示实例是否准备好接收流量，会检查数据库、缓存、channel layer、Celery broker、worker、beat、roundtrip 等依赖。

初学者理解：

- `live`：我还没死。
- `ready`：我现在能不能正常干活。

面试官可能追问：live 通过但 ready 不通过怎么办？

回答：

说明进程还活着，但依赖不可用，比如 DB 或 Redis 挂了。负载均衡应该停止给它分流，但不一定立刻重启容器。

### Q42：ready 检查为什么不能太重？

推荐回答：

健康检查调用频率很高。如果每次都做复杂数据库查询、Celery roundtrip 或 Redis 大量操作，探针本身会增加系统压力。所以 ready 检查需要 timeout、可配置开关和短 TTL 缓存。

### Q43：项目如何记录降级？

推荐回答：

项目里一些基础设施异常不会直接静默吞掉，而是记录 degraded counter。例如缓存锁不可用、聊天历史不可用、Celery 派发失败等。这样线上不只是看 500，还能知道某些功能正在降级。

## 16. 登录态与安全问答

### Q44：单会话控制怎么实现？

推荐回答：

服务端维护 `UserActiveSession`，记录每个用户当前有效的 session key。HTTP 请求经过中间件时，会检查当前 session 是否等于权威 session。如果用户在其他地方登录，旧 session 就失效。

WebSocket 是长连接，所以连接建立时要检查用户，接收消息时也要检查 session 是否仍然有效。

面试官可能追问：为什么要做单会话？

回答：

游戏类项目可能有资产、战斗和交易操作。单会话可以降低账号共享、多端同时操作导致状态混乱的风险。

### Q45：生产部署有哪些安全措施？

推荐回答：

生产 Docker Compose 里 Web 和 worker 容器使用：

- `read_only: true`：限制运行时修改应用目录。
- `no-new-privileges:true`：防止进程提权。
- `cap_drop: ALL`：去掉不必要 Linux capability。
- Redis 可以配置密码。
- 生产要求非 SQLite 数据库。
- nginx 负责静态资源和反向代理。

面试官可能追问：为什么静态文件不用 Django/Daphne 直接服务？

回答：

Daphne 更适合动态请求和 WebSocket。静态文件由 nginx 处理更高效，也更容易配置缓存、压缩和访问控制。

## 17. 性能与优化问答

### Q46：这个项目有哪些性能风险？

推荐回答：

主要风险有：

- 高频页面可能出现 N+1 查询。
- 后台扫描任务可能扫太多数据。
- 战斗计算可能占用 CPU。
- Redis 同时承担多个角色，故障影响面大。
- WebSocket 广播量大时 channel layer 压力增加。
- 事务太长导致锁等待。

### Q47：如何避免 N+1 查询？

推荐回答：

列表页和复杂装配逻辑要使用 `select_related` 和 `prefetch_related`。例如门客列表需要模板、装备、技能时，不能每个门客单独查一遍。可以把复杂查询封装到 selector/query 层，统一优化。

初学者理解：

N+1 就是：

```text
查 1 次列表
列表里有 N 条数据
每条数据又额外查 1 次关联数据
总共 1 + N 次查询
```

优化后应该尽量变成 2 到 3 次批量查询。

### Q48：后台扫描任务如何优化？

推荐回答：

扫描任务要有明确过滤条件和索引，比如 `status + complete_at`。每次扫描应该限制批量大小，避免一次处理太多。多 worker 扫描时可以考虑 `skip_locked`。处理时仍然要幂等和状态检查。

## 18. 常见技术细节追问速查

### Q49：为什么不用数据库存所有聊天消息？

回答：

世界聊天只需要短期最近消息，不需要复杂持久化查询。Redis List 更适合短期高频消息。如果后续有审计、举报、客服追溯需求，可以异步落库一份审计日志。

### Q50：为什么 Redis 不能替代 MySQL？

回答：

Redis 适合缓存和短期状态，但资产、库存、交易、拍卖结果这类强一致数据需要关系数据库的事务、约束和持久化能力。Redis 可以辅助，但不能作为最终账本。

### Q51：为什么任务状态要落库，而不是只放 Celery？

回答：

Celery 是任务执行系统，不是业务状态存储。建筑升级、任务运行、拍卖轮次这些状态需要用户查询、失败恢复和后台扫描，所以必须落数据库。

### Q52：如果 Celery 任务重复投递怎么办？

回答：

任务必须幂等。执行时重新查库、锁定记录、检查状态。如果状态已经完成，就跳过。不要靠“Celery 只执行一次”作为业务保证。

### Q53：如果用户连续点击按钮怎么办？

回答：

前端可以禁用按钮，但后端不能依赖前端。后端要通过事务、行锁、状态检查、幂等 key 或限流来保证重复请求不会破坏状态。

### Q54：为什么要用 `transaction.on_commit()`？

回答：

因为外部副作用应该在数据库提交成功后再执行。如果事务回滚了但通知已经发出，用户会看到不存在的奖励或状态。

### Q55：为什么管理命令很重要？

回答：

项目有大量 YAML 模板和运行期配置。管理命令可以统一导入模板、刷新缓存、校验配置、初始化数据，降低手工操作错误。

### Q56：为什么不能把所有业务都写在模型方法里？

回答：

模型方法适合单模型行为，但跨多个模型的复杂事务更适合 Service。比如拍卖结算涉及 `AuctionRound`、`AuctionSlot`、`AuctionBid`、`InventoryItem`、`Message` 等，放在某一个模型里职责会过重。

### Q57：为什么要有 `battle_debugger`？

回答：

战斗规则复杂，需要调试不同门客、兵种、技能和数值配置。调试器只在开发环境启用，不能作为生产功能依赖。

### Q58：如果要做接口化改造，你会怎么做？

回答：

不会直接全量重写。优先选择高交互或移动端需要的模块，比如地图、战斗、交易、门客详情，逐步抽成 JSON API。Service 层已经存在的业务逻辑可以复用，View 只换成 DRF/API 层。

### Q59：如果让你继续优化这个项目，你优先做什么？

回答：

我会优先做三件事：

1. 强化核心状态机的并发测试和压测，尤其是交易、拍卖、踢馆、门客状态。
2. 完善可观测性，比如任务耗时、失败率、降级计数、队列积压。
3. 梳理 YAML 热更新边界，明确哪些配置支持热刷新，哪些需要重启。

前端工程化也有价值，但从后端求职角度，当前项目最大的亮点和风险都在后端一致性和异步系统。

## 20. 面试时不要这么说

避免说法：

- “我用了 Redis 保证强一致。”
  更准确：强一致主要靠 MySQL 事务和行锁，Redis 用于缓存、广播、短期状态和限流。

- “Celery 保证任务只执行一次。”
  更准确：Celery 可能重复投递，所以业务任务要幂等。

- “SQLite 测试通过说明并发没问题。”
  更准确：SQLite 快速测试只能验证部分逻辑，真实并发要用 MySQL/Redis 测。

- “这个项目是前后端分离。”
  更准确：当前是 Django Template 为主，少量 JSON 和 WebSocket。

- “YAML 改了就一定能热更新。”
  更准确：部分运行期配置支持刷新，部分配置仍需要重启或导入数据库。

## 21. 初学者必须理解的核心概念

### 21.1 状态机

状态机就是一个对象有多个状态，并且只能按规则从一个状态变成另一个状态。

例如门客：

```text
IDLE -> DEPLOYED -> IDLE
IDLE -> TRAINING -> IDLE
IDLE -> WORKING -> IDLE
```

不能出现：

```text
TRAINING -> DEPLOYED
DEPLOYED -> WORKING
```

除非业务明确允许。

### 21.2 幂等

幂等就是同一个操作执行多次，最终结果不会重复变化。

例如领取奖励：

错误：

```text
点一次发 100 银两
点两次发 200 银两
```

正确：

```text
第一次领取成功
第二次发现已领取，直接跳过
```

### 21.3 最终一致

最终一致是指系统不保证立刻完成，但保证最终会被后台任务修正到正确状态。

例如建筑 10:00 完成，扫描任务 10:01 才处理，用户可能晚 1 分钟看到完成。这通常可以接受，比任务丢失永远不完成更可靠。

### 21.4 补偿

补偿就是前面操作成功了，后面失败了，需要把前面的影响撤回或修正。

例如世界聊天：

```text
扣小喇叭成功
广播失败
返还小喇叭
提示用户发送失败
```

### 21.5 降级

降级就是依赖服务异常时，不让整个系统崩掉，而是牺牲非核心功能。

例如：

- 聊天历史加载失败，仍允许页面打开。
- 在线人数统计失败，显示默认值。
- 但资产扣减失败不能降级成“假装成功”。

## 22. 最后总结怎么说

如果面试官问“这个项目最大的收获是什么”，可以这样回答：

这个项目让我最大的收获是：后端开发不只是写接口 CRUD，还要处理业务状态、事务边界、异步任务、失败补偿和基础设施异常。比如拍卖结算要考虑重复执行，门客出征要考虑并发占用，聊天要考虑扣道具后广播失败，YAML 配置要考虑校验和缓存刷新。我的核心思路是，高风险写路径用数据库事务和行锁兜底，异步任务做幂等，Redis 用在适合缓存、广播和短期状态的地方，真实并发语义必须用真实 MySQL/Redis 验证。
