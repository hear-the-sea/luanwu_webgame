# 玩家卡顿优化

2026-10-10 线上检查确认两个公网出口各占满 20 条实时连接槽，六类任务队列没有积压，主要页面抽样响应正常。两张擂台图片合计约 6 MB；Web 使用约 330 MB，容器上限为 384 MB。

## 已实现的应用优化

- 通知、聊天、在线统计在 `pagehide` 释放连接，在 `pageshow` 恢复。聊天保留未确认消息的操作编号，旧连接回调不能干扰新连接；身份失效的连接不会因页面恢复而重新连接。
- 连接异常或配额不足保留前五次快速恢复，持续失败时退避逐步增加到最多 60 秒。服务暂时不可用仍最多等待 15 秒；连接稳定 30 秒后重置退避。隐藏标签页继续接收通知。
- 两张擂台主图使用同尺寸 WebP；守擂历史的 88 像素预览使用 176 像素缩略图。PNG 原图保留。原图合计 6,355,663 字节，WebP 主图合计 866,700 字节，缩略图合计 14,828 字节。

## 服务器配置建议

[`docker-compose.performance.example.yml`](../docker-compose.performance.example.yml) 是待审阅的生产覆盖配置：Web 上限调整为 768 MB，同 IP 连接配额为 60。单用户 12 条、握手速率、来源校验与会话校验保持现有规则。

应用修改和该配置均尚未部署。加载顺序必须在现有 Compose 配置及本次镜像覆盖文件之后。先运行 `docker compose config --quiet`，备份原镜像与配置，再更新 Web；数据库、Redis 和其他正常 worker 保持运行。

配置调整仍有限额，不能替代客户端正确释放连接。客户端重试变慢能降低重复握手压力；同一出口超过现有配额的问题需要合理调高配额才能缓解。

## 发布后验证

- 用 `docker inspect` 确认实际 Web 内存上限；通过轻量 HTTP 探针检查 readiness，避免在 Web 容器内额外加载 Django 诊断进程。
- 检查新图片 URL 正常返回、页面使用缩略图；观察手机和桌面加载与历史展开交互。
- 对照近 30 分钟实时连接配额拒绝数量和活动槽数量；确认各队列执行心跳正常，并观察 Web 内存及重启计数。
- 多标签页、浏览器前进后退、网络短暂中断、账号异地登录时，验证释放、恢复、退避和终止行为。
